# dockwright (claude-orchestrator)

A Python tool that lets Claude Code sessions act as **managers** that spawn other Claude Code / Codex sessions (**workers**) into separate tmux windows, relay questions from workers to the human, and report status across all of them. Multiple managers can run at once, each scoped to its own workers.

The terminal layer is tmux: managers and workers each live in their own tmux window, spawned detached (`new-window -d`) so opening a worker never steals focus from the manager. Some legacy names survive from an earlier terminal driver: the env var `CLAUDE_ITERM_SID` and the `iterm_sid` key in some tool returns now hold a tmux **pane id**; records on disk write `window_id` (read back-compat via `state.window_id_of`).

Repo: your clone of the claude-orchestrator repository (`~/projects/.../claude-orchestrator/` by convention).

The **architect** (multi-repo ticket pipeline) is an **optional separate component, not included in this distribution** — a standalone MCP server exposing `architect_detect` / `architect_design`. Its per-ticket workdir lives under the state root at `architect/<ticket>/`. See the architect-pipeline skill; it's not covered here.

## Keep this skill in sync with the tool

**If you modify dockwright, you must also update this skill in the same change.**

Triggers for an update pass: MCP tools added/removed/changed signatures; hooks behavior changed; file-protocol changes (new dirs under the state root, renamed record fields); new `CLAUDE_*` env contract; items moving on/off the "What it can't do" list; breaking UX changes in the slash commands; new failure mode + workaround discovered. Stale skills are worse than no skill — they mislead.

## Mental model

```
       you                        you
        ↕                          ↕
  manager A (domain: general)   manager B (domain: reviews)   ← peer managers, each its own tmux window
   ↕     ↕                        ↕
  w1    w2                       w3        ← workers in a separate "claude-workers" tmux session
```

- **Regular** claude session: no agent overlay, no orchestrator. Most sessions.
- **Manager**: opt-in via `/manager [domain]`. Gets an auto-rolled funny `<adjective>-<mythical-creature>` name (e.g. `happy-dragon`) — that name is the routing key for its workers' events. Multiple managers can coexist; each sees only its own workers (strict per-manager routing via `parent_manager_name`). Talks to the user, orchestrates workers, never edits code itself. Managers run the `claude` runtime.
- **Worker**: spawned by a manager (runtime `claude` or `codex`). Lives in its own window inside a dedicated **`claude-workers` tmux session**. Has `ask_manager`; must never call `AskUserQuestion` (headless — it would wedge). Gets a routing `name` (task label) plus a cosmetic `funny_name`; its tab title is color-coded by state (gray idle / yellow processing / red awaiting-human). Claude workers inherit all global rules / skills / MCPs; Codex workers get an injected worker-protocol bootstrap prompt.

**Key constraint**: no mid-turn interrupts. `send_manager_to_worker` types the message into the worker's pane via the terminal driver's send-text; if the worker is mid-turn, tmux buffers it and it submits on the worker's next idle. `ask_manager` blocks the worker's turn until the manager answers — bounded at 12 h with a progress keepalive (1500 s when the client sends no progress token; Codex keeps its provider bound) per call; on timeout the worker gets a `NO_ANSWER_YET:` sentinel and re-calls with `resume_question_id`, so the wait continues without duplicating the question, and the worker's MCP server keeps servicing other tools meanwhile.

## Architecture

| Component | Where | Purpose |
|---|---|---|
| Python package | `src/dockwright/` | FastMCP server + spawner + hooks + monitor CLI |
| Agent files | `~/.claude/agents/{manager,worker}.md` — **composed** by `setup.sh` from `deploy/agents/{manager,worker}.core.md` + overlay drop-ins + `{{vars}}`; beside each role manifest, compose also writes `~/.claude/roles/<Role>/role.<launch>.md` and `role.settings.json` (§ Roles) | System-prompt overlays for the two roles; the role renders a session launches in |
| Slash commands | `~/.claude/commands/` (source: `deploy/commands/`) | `/manager`, `/manager-resume`, `/manager-close`, `/recreate-manager`, `/manager-assign`, `/tab` |
| Hooks | `~/.claude/settings.json` (+ `~/.codex/hooks.json`) | `SessionStart`, `UserPromptSubmit`, `Stop`, `SessionEnd` shell out to `dockwright <sub>` |
| State broker | state root (`[paths].state_root`, default `~/.claude/dockwright/`) | File-based — atomic JSON writes, dir per concept |
| Manager memory | `~/.claude/dockwright/manager-memory/<domain>/` | Distilled per-session journals (outlives state cleanup) |
| tmux spawner | `spawner.py` + `terminal.py` | `tmux new-window -d`, env-var contract, claude/codex command building |
| Helper scripts | `~/.claude/scripts/` (source: `deploy/scripts/`) | `stale_monitor.py`, `preflight_cleanup.py`, `bootstrap-recreate.sh` |

The MCP server is one stdio FastMCP process per session. Every session (manager OR worker, claude or codex) connects to its own instance; all read/write the shared filesystem state. **Deployment model**: `src/` runs via `pip install -e` (hooks live on the next fire; `mcp_server.py` needs a session restart — that's what `/recreate-manager` is for), while the agent files are **composed** and the other copies (`commands/`, `scripts/`, `presets/`, `skills/`) are `cp`/`rsync`-deployed by `./setup.sh` — full when-does-it-go-live decision table in § Deployment surfaces below.

**The compose seam.** The deployed agent files are not stored verbatim — they are RENDERED at install time from three inputs:

1. **Core** — `deploy/agents/{manager,worker}.core.md`: the generic, operator-free prompt bodies, carrying `<!-- overlay: <name> -->` insertion markers and `{{var}}` placeholders. `worker.core.md` holds only `<!-- include: <fragment> -->` lines: its text and its markers live in `deploy/roles/fragments/`, and compose inlines each fragment before it places drop-ins.
2. **Overlay drop-ins** — `<overlay_dir>/<agent-stem>/*.md` (overlay_dir = `[paths].overlay_dir`, default `~/.claude/dockwright-overlay/`). Each drop-in optionally names an `insert_at: <marker>` in its frontmatter; matched drop-ins replace that marker line (sorted by filename), unbound ones append at end-of-file. The overlay lives in place at `config.overlay_dir()`, tracked and maintained by the operator (nothing to "install"); edits there — or in `dockwright.toml [agent_vars]` — take effect on the next `setup.sh` / `dockwright compose`. The drop-ins of `manager`, `worker` and `dockwright-reviewer` move to `<roles_dir>/{Manager,_shared,CodeReviewer}/overlay/` once that role has a manifest (for `_shared`, once any role has one); from then on compose refuses a file left in the agent-stem directory, and refuses a role drop-in that lands in no role render.
3. **Vars** — `{{name}}` substitutions from `deploy/agents/vars.defaults.toml` `[agent_vars]` (the generic defaults), overridden per-key by the operator's `dockwright.toml [agent_vars]`.

`dockwright compose` (invoked by `setup.sh`) writes the merged text to `~/.claude/agents/` and records provenance in a SIDECAR `.compose-stamp.json` in the out dir — never an in-file header, so the deployed agent files carry only prompt content. Composing a core file with no markers and no vars returns it byte-for-byte (the identity guarantee the byte-equivalence gate rests on).

## Multi-manager routing

| Routes by | Covers |
|---|---|
| `parent_manager_name` (per-tab, per-manager) | workers, questions, done events, wait_for_worker |
| `domain` (per pool) | manager-memory dir |

Same domain, multiple managers = isolated worker pools, shared memory. Different domains = nothing shared. `/manager [domain]` (default `general`); managers get `<adjective>-<mythical-creature>` names, workers `<adjective>-<animal>` (`names.py`); the statusline shows a non-`general` domain.

Routing is strict: `parent_manager_name == null` records are invisible to per-manager calls. Orphans: `_backfill_legacy_workers` adopts them on a single-manager `become_manager` boot, or a wildcard caller (`manager_sid=None`) sees them.

## Deployment surfaces — when to run setup.sh after merging an orchestrator change

Four independent surfaces receive an orchestrator change. What you must do depends on which file changed: (In every case that calls for `setup.sh`: it refuses (exit 4) while `~/.claude/dockwright/active/` shows registered live sessions — check the fleet first (`list_workers`/`list_managers` or `ls` that dir) and either wait for a quiet fleet or run a deliberate `DOCKWRIGHT_SETUP_FORCE=1` deploy.)

1. **Editable Python package — `src/dockwright/`.** `dockwright` is a `pip install -e` console-script that imports from `src/` directly, so on-disk changes are live the moment the local clone is on merged main. No `setup.sh`, no recreate. But it splits by process lifetime:
   - **Hooks** (`dockwright session-start|stop|user-prompt-submit|session-end`) run as a fresh subprocess each fire → they pick up `src/` changes immediately, for **newly-started sessions / the next hook fire** only.
   - **MCP server** (`dockwright mcp-server`) is long-running, started at manager/worker boot, and caches the package in `sys.modules`. A change to MCP tool code (`mcp_server.py`) is **not live in already-running sessions** until that session restarts.
2. **Composed agent files — need `setup.sh` (or `dockwright compose`).** The agent files are no longer copied; they are RENDERED from `deploy/agents/*.core.md` + overlay drop-ins + vars (see § The compose seam). A change to any core file, drop-in, or var is **not live until a recompose runs**. `dockwright compose --check` (also run by `dockwright doctor`) recomposes in memory and flags a stale deployed set.
3. **Other `cp`/`rsync`-deployed copies — need `setup.sh`.** `setup.sh` copies these into `~/.claude/`: `commands/*.md`, `scripts/*.py|*.sh`, `statusline-command.sh`, `presets/`, `skills/`. A change to any of these is **not live until `setup.sh` runs**. The Codex home is rebuilt from `~/.claude` on every run (`dockwright translate-codex`, § Translation to Codex) — edit the Claude sources, never `~/.codex/AGENTS.md`, `~/.codex/skills/<name>` or `~/.codex/agents/*.toml`.
4. **Settings / MCP registration.** `setup.sh` also merges the hooks snippet into `~/.claude/settings.json` and `~/.codex/hooks.json`, then registers the MCP via `claude mcp add` and `codex mcp add`. Only relevant on first install or when hook wiring changes.

Decision rule after merging a change:
- Changed a core agent file, an overlay drop-in, or an `[agent_vars]` value? → **run `setup.sh`** (or `dockwright compose`) to recompose.
- Changed another `cp`-deployed file (command, statusline, script, preset, skill)? → **run `setup.sh`**.
- Changed hook logic (`hooks.py`)? → live on the next session's hook fire via the editable install; no `setup.sh`. Already-running MCP servers are unaffected (hooks aren't MCP-resident).
- Changed MCP tool code (`mcp_server.py`)? → **recreate the manager** (and respawn workers) to restart the cached server; `setup.sh` alone won't do it.
- Changed `src/dockwright/` while `dockwright board --serve` runs? → **restart the board server**: stop the first of these whose `ps -p <pid> -o command=` shows `board --serve`: the pid in `<state_root>/board-serve.pid`, then the pid `lsof -ti tcp:<its port> -sTCP:LISTEN` prints. Then start it again from the main clone (`nohup dockwright board --serve --port <its port> > <state_root>/board-serve.log 2>&1 & echo $! > <state_root>/board-serve.pid`).

## File protocol

The state root is `[paths].state_root` (default `~/.claude/dockwright`):

```
<state_root>/
├── active/<sid>.json                  per-session record: name, funny_name, agent, cwd, window_id,
│                                      pid, state (idle|processing), domain (managers),
│                                      parent_manager_name + parent_name (workers; the old key is
│                                      written for one more release), parent_sid, kind, depth,
│                                      runtime (claude|codex), provider,
│                                      last_summary, last_turn_at,
│                                      human_attached_at (his last typed line; the flag holds 40 min)
├── questions/<manager>/<qid>.json     pending worker question (legacy unscoped: flat questions/<qid>.json)
├── questions/by-task/<key>/<qid>.json  its topic copy when the asker holds a topic (subworkers excepted); readers count each qid once
├── answers/<qid>.json                 manager reply → worker (worker polls + unlinks after read)
├── done/<manager>/<sid>-<eid>.json    explicit worker_done events (legacy/unscoped: done/_unscoped/)
├── turn-ends/<manager>/<sid>-<ms>.json  worker turn-end markers written by the Stop hook
├── closed/<sid>.json                  archived worker records (SessionEnd or idle auto-close) — resume_worker reads these
├── pause/manifest.json                the fleet-pause manifest; while it and daemon-stop both exist the pages lane prints
│                                      no DAEMON_STOPPED, and doctor lanes:mode passes
├── handoffs/<handoff_id>.json         manager→manager recreation snapshots
├── manager-triggers.jsonl             append-only log of handoff takeovers
├── children/<assignment_id>/r<N>.{brief.md,report.md,log}  headless child round files
├── presets/<name>.md                  spawn-prompt boilerplate (spawn_worker preset= prepends it)
├── slots/<category, URL-quoted>.json  worker-slot semaphore state (+ .lock); `staging:o/r` is one flat file
├── architect/<ticket>/                architect per-ticket workdir (blackboard.db etc.)
├── .seen-{questions,done,turn-ends}-<manager>   monitor cursors (one-shot scans persist SEEN here; questions by qid)
├── .stale-emitted.json                stale_monitor edge-trigger dedup state
└── manager.lock                       LEGACY — no longer read or written by any code; ignore
```

Manager memory is **outside** that tree: `~/.claude/dockwright/manager-memory/<domain>/<YYYY-MM-DD>-<sid>.md`.

All JSON writes are atomic (`tmp` + `os.replace`); `read_json` treats missing and corrupt as None. Routing rule: a record/event with `parent_manager_name == X` is visible only to manager X; `parent_manager_name == null` (legacy) events go to the `_unscoped` bucket, invisible to scoped calls — recovery is `_backfill_legacy_workers`, which runs on `become_manager` when exactly one manager is active and adopts the orphans.

## MCP tools (the `dockwright` MCP)

Most manager-side read tools take `manager_sid` — the caller's **own session UUID** (NOT the funny name; passing the name degrades the filter to wildcard with a stderr warning). `None` = legacy wildcard.

**Manager-side:**

| Tool | Effect |
|---|---|
| `become_manager(claude_sid, iterm_sid?, domain?, name?)` | Registers this session as a manager. Rolls a funny `<adjective>-<mythical-creature>` name (unique across active records; pass `name` to preserve an existing identity — the `/manager-reboot` lane), defaults `domain="general"`. Runs legacy-worker backfill + same-pid ghost pruning. Returns `{ok, name, domain, runtime, preflight}`. No lock — multiple managers coexist. |
| `spawn_worker(initial_prompt, name?, cwd?, extra_args?, env?, preset?, manager_sid?, runtime?, task_key?, force?)` | Opens a window in the `claude-workers` tmux session (creates it if missing). `extra_args` carries `--model` and `--effort`; a Claude worker launch without both is refused. `name` auto-suffixes `-2`, `-3` on collision. `preset` prepends `<state_root>/presets/<name>.md`. `manager_sid` stamps `parent_manager_name` (via `CLAUDE_PARENT_MANAGER` env) so events route back; a sid matching no live manager (or a worker/nested record) → ValueError, nothing spawned; `manager_sid=None` = deliberately unscoped. `runtime="codex"` launches Codex with `--ask-for-approval never --sandbox danger-full-access --dangerously-bypass-hook-trust` + a bootstrap prompt; Claude workers get remote-control-off `--settings` and the composed worker agent definition as `--append-system-prompt-file ~/.claude/agents/worker.md` (the harness reads it at launch; the file must have a body); a caller `--system-prompt[-file]`/`--append-system-prompt[-file]` suppresses it. `env` can add vars but can't override orchestrator-controlled keys (`CLAUDE_AGENT`, `CLAUDE_WORKER_NAME`, `CLAUDE_WORKER_RUNTIME`, `CLAUDE_WORKER_PROVIDER`, `CLAUDE_ORCH_ACCOUNT`, `CLAUDE_CONFIG_DIR`, `CLAUDE_PARENT_SID` and `CLAUDE_WORKER_KIND`, which the spawner sets itself). |
| `list_workers(manager_sid?)` | Worker records + last assistant turn from transcript + `alive` (PID check). |
| `list_pending_questions(manager_sid?)` | Pending questions, oldest first. |
| `ask_engineer(claude_sid, question, task_key?)` | Records a non-blocking question to the engineer on `task_key` (default `fleet-<your domain>`); it sits in the board's Inbox until answered. The answer comes back as an `ANSWER` line in your tab pointing at `decision.q-<id8>` only when he answers on the board or with `dockwright topic message --kind answer`; a close by a tool call (`answer_question`, `answer_child`, `topic_message`) pages nothing. |
| `answer_question(question_id, text, decided_by="manager")` | Writes `answers/<qid>.json`, unlinks the question. A keyed worker's question also gets a `decision.q-<id8>` record with `decided_by` (`manager` \| `engineer`) in its body and frontmatter. A manager's question to the engineer gets no `answers/` file and no `ANSWER` line from this call: after closing another live manager's question, tell it with `send_manager_to_manager`. |
| `send_manager_to_worker(worker, text, auto_resume=false)` | Types the content **directly into the worker's pane**, prefixed `[MANAGER] ` (bracketed paste + single Enter — multi-line safe). tmux buffers if the worker is mid-turn. No inbox file EVER — RAISES when the worker has no live window. With `auto_resume=true`, a closed worker with a resumable transcript is resumed and the message delivered in one call (result carries `resumed: true`); still RAISES when nothing is resumable. Status: `delivered`, or `human_attached` (`delivered: false`, `until`, `explanation`; nothing typed) while the engineer is attached to the worker — 40 min after his last typed line, or until `set_human_attached(name, false)`. His own topic messages, gate verdicts and the engine's merge wakes still type when his input line is idle; a refused one retries each lane pass, and its reason names the line (`draft`, `queued`, `no prompt`, `no capture`). |
| `send_manager_to_manager(name, text)` | Message a **peer manager** by funny name. Idle-guarded: peer's input box empty → types directly (`delivered_live`), prefixed `[MANAGER <sender name> · <sender domain>] ` — the sender comes from its own active record, never a caller argument, so a leading slash arrives as plain text; the result carries `sender` (null when the record could not be resolved, which degrades the prefix to `[MANAGER] `); human mid-typing → does NOT type (`peer_busy`, delivered=False) — no inbox; RAISES when the peer has no live/readable window. |
| `list_managers()` | All active managers: name, domain, sid, window id, runtime. |
| `kill_worker(worker)` | Drops pending questions, then **gracefully closes the worker's tmux pane** so the worker's SessionEnd hook fires (selffix retro + closed/ archive). Not SIGTERM. Refused with the way out while the worker is human-attached. |
| `set_human_attached(name, attached)` | Arms the worker's human-attached flag for 40 min from now, or drops it. No page either way; `list_workers` rows carry `human_attached` and `human_attached_until`. |
| `get_worker_summary(worker)` | The worker's full report: its newest `worker_done` summary since its last tasking or turn start and no more than 600 s before its latest turn end (the dones `FINISHED_SILENTLY` counts), else its full last assistant message; `source` (`worker_done` \| `transcript`) says which. A line queued during the worker's turn does not move that start. |
| `get_worker_tail(worker, lines=50)` | Last N transcript entries (role + 200-char preview). |
| `attach_existing(manager_sid?)` | Called on `/manager` startup: surviving workers + orphan questions. |
| `list_closed_workers(manager_sid?, limit?)` | Closed/auto-closed worker records, newest first. |
| `resume_worker(name)` | Reopens a closed worker in its original cwd via `claude --resume <sid>` / `codex resume <sid>` — full history restored, `parent_manager_name` preserved. Deletes the closed record only after the resumed session re-registers (else `{ok: false}` and the record stays for retry). |
| `prepare_handoff(claude_sid, narrative_summary, trigger_reason)` | Snapshots workers + questions into `handoffs/<id>.json` AND distills the transcript into manager-memory. |
| `spawn_replacement_manager(handoff_id)` | Opens a new window (in the old manager's session) with initial prompt `/manager-resume <handoff_id>`. |
| `become_manager_with_takeover(claude_sid, takeover_from, handoff_id, iterm_sid?)` | Atomic takeover: closes the old manager's window, inherits its name + domain (so workers' `parent_manager_name` stays valid), marks the handoff consumed, logs to `manager-triggers.jsonl`. |
| `close_manager_self(claude_sid)` | `/manager-close`: synchronously distills memory, removes the active record, closes own window. |
| `topic_set(task_key, actor_sid, priority?, title?, domain?, status?, blocked_by?, links?)` | Changes a topic card, `artifacts/<task_key>/topic.json`: priority P0–P3 (default P2), title, domain, status open/closed (note, lane and fleet topics only), blocked_by (topic keys, replaced whole), links `{pr, ticket, worktree}` (merged; null erases; `worktree` on note, lane and fleet topics only — move a work's with `pipeline_advance(cwd=)` or `pipeline_rework(cwd=)`). `pipeline_start` writes a work's card, and the engine rewrites its worktree and kind from the main token's committed cwd and running schema whenever a commit, override or schema snapshot moves them; `pipeline_status` prints it and shows the priority one step higher while the work waits on a human. Logs a `topic_set` event. |

**Worker-side:**

| Tool | Effect |
|---|---|
| `ask_manager(claude_sid, question, resume_question_id=None)` | Writes `questions/<manager>/<qid>.json` (plus `questions/by-task/<key>/<qid>.json` when the worker holds a topic), polls `answers/<qid>.json` every 500ms (async — other tool calls on the same worker stay serviceable), returns the answer. Server-side timeout of 12 h with a progress keepalive (1500 s when the client sends no progress token; Codex keeps its provider bound) returns a `NO_ANSWER_YET:` re-ask sentinel; re-call with `resume_question_id` to keep waiting on the SAME pending question. Self-heals on corrupt answer files. |
| `worker_done(claude_sid, summary)` | One-shot done event in `done/<manager>/`. Worker's REQUIRED last action on task completion. |
| `wait_for_worker(name, timeout_sec=3600, manager_sid?)` | Block until that worker writes a done event (`{found: "done", summary}`) or its session exits (`{found: "exited"}`). Lets workers (or the manager) chain on a sibling's completion. |
| `acquire_worker_slot(claude_sid, category, max_concurrent?, timeout_sec=1800, task_key?, node?, ttl_sec?, wait=True)` | Per-category semaphore so N workers don't OOM the host on `mvn test` etc. Default cap: `mvn=5`; override per call or via env `CLAUDE_ORCH_SLOTS_<CATEGORY>`. Stale holders auto-evicted. With `task_key` (or `wait=False`) the slot is a lease: owned by the work (or `session:<sid>`), kept by its expiry (`ttl_sec`, default `[pipeline] lease_ttl_sec` 7200) rather than by the session, renewed by a repeat call of the same owner; the answer carries `acquired`, and `wait=False` on a held category answers `{acquired: false, holders}` at once and records a work as a waiter. Pair with… |
| `release_worker_slot(slot_id)` | …release. Idempotent. `pipeline_close` releases every lease and waiter of the work. |

There is no `register_self` MCP tool and no `send_instruction` — registration happens in the SessionStart hook; instruction delivery is `send_manager_to_worker`.

### Role-neutral protocol names (aliases, both work)

The parent↔child protocol is one mechanism at every layer; manager↔worker is its first instance.
The old names stay as thin aliases until the manager rules their descriptions carry have a home under the new names.

| new (canonical) | old (alias) | difference |
|---|---|---|
| `spawn_child(parent_sid, brief, name?, cwd?, task_key?, env?, provider?, model, effort?, mode, context?, role?)` | `spawn_worker(...)` | `parent_sid` required — a live manager's or a live worker's sid; a worker's child registers as `kind=subworker` at depth parent+1, defaults to the parent's cwd and the name `<parent>-child`, and is refused when its depth would reach `[subworkers] max_depth` (default 3). `provider` names who runs the child — a worker's defaults to `[subworkers] default_provider` (`codex-exec`), a manager's to `claude-tui`. `model` is required; `mode` is `report` or `interactive`, required for `claude-tui` and `codex-exec`; `effort` is required for `claude-tui` and `claude-exec` and refused for `codex-exec`; `context` names the role manifest a `claude-tui` or `claude-exec` child loads (GenericWorker when omitted; a `claude-exec` report child takes the role's Codex render); `role` is gone with the roster and refuses any value. Legacy `extra_args`/`preset`/`runtime`/`force` stay on the alias |
| `ask_parent(child_sid, question, resume_question_id?)` | `ask_manager` | sentinel names `ask_parent` |
| `answer_child(question_id, text, decided_by)` | `answer_question` | — |
| `child_done(child_sid, summary)` | `worker_done` | — |
| `wait_for_child(name_or_sid, parent_sid, timeout_sec=1500)` | `wait_for_worker(name, timeout_sec=3600, manager_sid?)` | returns `found="timeout"` instead of raising; returns `found="question"` with the child's unanswered question (answer with `answer_child`, call again) where the alias keeps waiting; refuses an empty/dead `parent_sid`; default 1500 s vs 3600 s; both accept a name or a sid (one implementation). A parent passes its own sid for its own children — a manager's or a worker's; a worker waiting on a sibling passes the `parent_sid` from its own active record — `$CLAUDE_PARENT_SID` is the spawn-time copy and goes stale when the manager is recreated. |
| `list_children(parent_sid)` | `list_workers(manager_sid?)` | `parent_sid` required — a manager's or a worker's own sid; refuses an empty or dead `parent_sid` where the alias degrades to the wildcard list with a stderr warning; rows carry `question_pending` |
| `send_to_child(name, text)` | `send_manager_to_worker(worker, text, auto_resume?)` | legacy `auto_resume` stays on the alias |
| `kill_child(name)` | `kill_worker` | — |
| `get_child_tail(name, lines?)` | `get_worker_tail` | — |
| `pipeline_child(claude_sid, task_key, child, lane?, message, close?, cut?, codex_message?, role?)` | — | a node of a schema that declares children starts and continues them only through this tool; `spawn_child` refuses it. `lane` names one of the slot's lanes (default its first); `role` names a row only on a snapshot taken before roster-removal. The Claude leg of a `pipeline_child` child is named `<parent>-<role-slug>[-w<work round>][-e<entry>]-r<N>`, N counting within that work round and entry; the two segments appear only above 1; the Codex leg keeps `<parent>-child` |

Every session record carries `kind` (`manager` | `worker` | `subworker`), `parent_sid`, `parent_name`, `depth` (manager 0, worker 1, subworker 2), `provider` beside `parent_manager_name`; readers use `parent_name` with a fallback to the old key. A subworker is `agent=worker` in the file protocol — its events land in its parent worker's buckets, and a manager's scoped calls never see it. `[subworkers] max_depth` in `dockwright.toml` (default 3) is the first depth `spawn_child` refuses to create.

### Child providers and the Codex gate

Three providers ship. `codex-exec` runs `codex exec` headless in its own tmux window; `claude-exec` runs `claude -p` headless; `claude-tui` is the interactive Claude child. `mode="report"` switches the dockwright MCP off — the child's final message is the report and it cannot ask anything; read-only is enforced per provider: `codex-exec` runs under `-c sandbox_mode="read-only"`, so the kernel sandbox refuses writes, plus `-c approval_policy="never"`, which refuses every tool escalation including a call to another MCP server; `claude-exec` runs under `verifier-settings.json`, which denies the edit tools and the mutating git verbs but is a denylist, not a sandbox. `mode="interactive"` leaves `ask_parent`/`child_done` available. `mode` and `model` apply to headless providers and to a `claude-tui` child, where `mode` picks the settings preset (`report` → `verifier-settings.json`).

`[codex] allowed_roots` in `dockwright.toml` is the gate: empty by default (Codex disabled everywhere), and a malformed value also reads as disabled. It is checked in `spawn_worker_tab` before any side effect, so it covers every Codex launch — `spawn_child`, `spawn_worker(runtime="codex")`, `resume_worker` of a Codex record, and every `send_to_child` round. `[subworkers] default_provider` picks a worker's child provider (`codex-exec`); `[subworkers.providers.<name>]` holds `ask_parent_wait_sec` (240 for `codex-exec`, which also raises the Codex client's MCP timeout; 1500 for `codex-tui`) and, for `claude-exec`, the topic agent's `model` and `effort`; a child's model comes from its `spawn_child(model=)` call.

A worker record carries `provider`, written by SessionStart from `CLAUDE_WORKER_PROVIDER` and falling back to the runtime's TUI provider. Round files live at `<state_root>/children/<assignment_id>/r<N>.{brief.md,report.md,log}`, and the assignment record carries `provider`, `mode`, `model`, `round`, `round_started_at`, `report_path`, `log_path`, `rounds_dir` and `spawn_env`.

`wait_for_child` reads the report file before done events and returns it as `found="done"` with `report_path` and `round`; it waits 5 s for a late report after the record vanishes, then reports `session_ended_without_report`. `send_to_child(name, text)` on a closed headless child opens the next round with the same provider, env and arguments in a new window `<parent>/<child> rN`, and refuses while a round is still running; `completed_early: true` in its result means the round ended before its registration was observed — `wait_for_child` still decides between the report and `exited`. Calling `send_to_child` right after `wait_for_child` returned `done` can be refused with "shutting down": the next round opens only once the child's record has reached `closed/`, which its SessionEnd hook does a moment later — retry for a few seconds rather than respawning the child. `resume_worker` refuses a headless child and points at `send_to_child`; `kill_child` closes the dead window a finished round left open. A claude-tui child's next round is `send_to_child`, then `wait_for_child`; a wait without the send returns the previous report. A child that `pipeline_child` started takes its next round only through `pipeline_child`: `send_to_child` refuses it until its slot closes.

A subworker is supervised by liveness only: the stale monitor never nudges, pages or autocloses it; the one exception is the safeguard dialog, which the lane clears on an interactive child (`claude-tui`) as on a worker, naming the parent in the page (`SAFEGUARD_PAUSE <child> (child of <parent>) → get_child_tail(...)`). It folds its activity into its parent's stall clock, and — when the parent worker is gone for 120 s — archives it as `closed_reason: "orphaned:<parent>"`, closes its windows, and records `ORPHANED_CHILD` on the owner's lane without printing it (a silent kind, § Lane monitors). Superseded round windows are closed by the monitor; the latest round's window stays for `kill_child`. A Codex child's `spend` is read per round from `children/<assignment_id>/r<N>.log` (`turn.completed`), with `in_tokens` net of the cache and no money. `send_to_child` and `resume_worker` refuse a child whose parent is not live. On the tmux bar the child is `↳ <name> · <runtime>` right after its parent, and a worker with a live child is never `💤`.

### Lanes

A child slot of a pipeline schema names its lanes. A slot with one lane writes `role`, `mode`, `model`, `effort` and an optional `codex` in itself; a slot whose node picks the reviewer by the files of the diff writes one `[nodes.<n>.children.<slot>.lanes.<name>]` table per lane with the same five keys. `role` is the manifest the child loads (`CodeReviewer`, `DocReviewer`), `mode` is `report` or `interactive`, `model` is a `@<family>` token or a concrete `claude-<family>-<version>` id, `effort` one of `low`, `medium`, `high`, `xhigh`, `max`, and `codex` a concrete Codex model id. `pipeline_child(lane=)` picks the lane (default the first); the engine starts the Claude leg as a `claude-tui` child on the lane's model, effort, role file and preset, and the Codex leg on the lane's `codex` when `[codex] allowed_roots` covers the node's cwd. `dockwright schema show <schema>` prints each slot as `child <slot>: lanes=<name>:<role>/<mode>/<model>/<effort>[+codex <id>]`. A snapshot taken before roster-removal keeps `roles` on its slots: `pipeline_child(role=)` names a row there, read from the operator's legacy `~/.claude/dockwright-roster.toml` for one release (`dockwright doctor` `config:legacy-roster`), and such a slot starts no Codex leg.

### Translation to Codex

`dockwright translate-codex` (run by `setup.sh`, only when `codex` is on PATH) makes Claude the source of truth for Codex: `~/.claude/rules/*.md` → one `~/.codex/AGENTS.md` (alphabetical, each rule between `<!-- BEGIN rules/<name> -->`/`<!-- END … -->`, first line a generated marker); every `~/.claude/skills/<name>/` except `plannotator-*` → `~/.codex/skills/<name>/` verbatim; every `~/.claude/commands/*.md` → `~/.codex/skills/<cmd>/SKILL.md` unless a skill of that name exists (skill wins) or the command's frontmatter sets `disable-model-invocation: true` (the model may not invoke it, so it is not offered to Codex as a skill); every `~/.claude/agents/*.md` → `~/.codex/agents/<stem>.toml`; every `~/.claude/roles/<Role>/role.codex.md` → `~/.codex/roles/<Role>.md`. `~/.codex/.dockwright-translate.json` records what it wrote; anything found at a target path and not in the stamp is moved to `~/.codex/.dockwright-translate-backup/` first (write-once), an owned target whose source vanished is removed only when the disk still holds exactly what was written, and everything else in `~/.codex` — `skills/.system/`, foreign skills, `config.toml`, `hooks.json`, execpolicy `.rules` — is untouched. The one move beyond that: `~/.codex/rules/*.md` → `~/.codex/.dockwright-translate-backup/rules/`, and that directory goes only when the move leaves it empty. Every write, move and removal is confined to the real Codex home: a target reached through a symlink that resolves outside it is skipped with a warning and left out of the stamp, `--check` reports it as `resolves outside CODEX_HOME`, and a symlinked `~/.codex/rules` is left alone. `dockwright translate-codex --check` and `dockwright doctor` (`codex:translation`) tell a stale Codex home from a fresh one. Flows are not translated — skills reference `~/.claude/flows/*` by absolute path, and Codex's read-only sandbox reads `~/.claude`. Plugin skills are not translated — only `~/.claude/skills/` is walked. `dockwright render-agents-md --out FILE SRC…` is the same concatenation over arbitrary sources for a repo layer.

## Roles

A role is a manifest, `~/.claude/roles/<Role>/role.toml` (`[paths] roles_dir`): `core` (a core in `deploy/roles/`, `deploy/roles/subagents/` or `deploy/agents/`) or `extends`, `launch`, `actions` and `reachable` (verbs from `roles/actions.toml`), `fragments` (the manual list; it stands while `[roles] computed` is unset), `skills` (`["*"]` lists every skill), an optional `profiles` (the project profiles the role renders for; default every `[profiles.sets]` entry), `profile_excludes` (project units the role drops until the ruling) and a `[settings]` profile: `claudeMdExcludes`, `skillOverrides`, `skillListingMaxDescChars` and `disabledMcpjsonServers` (project `.mcp.json` servers the session does not start). An `extends` child unions its lists with the parent's and never removes a name.

A unit is a `.md` file with frontmatter `kind: guard|fact|ruling|pointer`, `binds: [<verb>, …]`, `domain: <domain>` and optional `cites: [<verb>, …]`; `roles/actions.toml` holds the `[actions]` and `[domains]` vocabulary. Units live in `roles/_shared/fragments/<domain>/` (the pool: the folder is the domain), `roles/<Role>/fragments/`, `deploy/roles/fragments/` (the canon; the two protocol fragments carry no frontmatter) and the project layer `[paths] project_units_dir` (one folder per domain, a unit's home is its own `domain`). A `guard` binds a role when a verb of its `binds` is in the role's `actions` or `reachable`; every other kind binds on `actions` alone. `roles/<Role>/overlay/` and `roles/_shared/overlay/` hold drop-ins; a Manager drop-in with frontmatter is a catalog unit that no role computes.

`[profiles]` in `dockwright.toml`: `[profiles.sets]` names each profile as a list of domains (`none = []` is implied), `[profiles.repos]` maps a repository or home basename to a profile, `work_roots` and `work_default` give every other directory under a work root its profile, and `personal_owners` keeps a clone whose `origin` owner is listed on `none`. `dockwright role-args <Role> --launch <L> --cwd <dir>` and every launcher resolve the profile of the session's cwd. `[subagents]` maps a subagent type to `{ role = "<Role>", core = "<core>" }` and `default_role` names the role whose bundle a `SubagentStart` pointer cites.

`dockwright compose` renders, beside each manifest, `role.<launch>.md` and `role.<launch>.<profile>.md` for every launch and profile, `role.codex[.<profile>].md` when `launch` holds `worker` or `child`, and `role.settings.json`: `skillOverrides` sets every skill and command the manifest does not list to `name-only`. A profile render carries the role's units, then the profile's units, before the protocol; its second line is `<!-- dockwright-profile: <p> -->`. It also writes `roles/_profiles/<p>.md` (a profile's units alone), `roles/_agents/<p>.json` (the `[subagents]` definitions for `--agents`: each entry's `prompt` is the role's `agent` render on that profile, with `description`, `tools` and `model` from the core's frontmatter), `roles/catalog.json` and `roles/catalog.md` (every unit with its kind, binds, domain, home, the roles that name it by hand and by computation, and the files that cite it), and `agents/<type>.md` for each `[subagents]` entry on profile `none`. `dockwright roles catalog --report` prints the discrepancies between the manual lists and the computation; `--write-baseline` records in `roles/catalog.baseline.json` the guards among each role's and each subagent's units outside the project layer, and refuses while a `[[drop]]` in `roles/rulings.toml` names a guard that a render holds again, or while check (j) reports a lost guard. `--check` reports a guard that left a render since (check (j)), and reads a baseline an earlier version wrote by its `guards_manual`, failing a role entry written from an empty manual list. A role layer never loosens a stricter `skillOverrides` value the launch's own settings carry.

Launch kinds: `worker` (a tmux worker or pipeline node; the render ends with `worker-protocol`), `child` (a subworker; ends with `child-protocol`), `manager`, `lane`, `interactive` (the operator's own session, the `Engineer` role) and `agent` (a subagent definition; no protocol). A Claude session gets the render through `--append-system-prompt-file` once, one `--settings` file (the launch site's preset merged with `role.settings.json`), and `--agents-file <roles>/_agents/<p>.json` when that file exists. `dockwright launch <args…>` execs `claude` with `--agents-file <path>` expanded into `--agents <json>` with no shell in between (tmux takes no command over 16 KB); every tmux launcher starts `claude` through it, and a headless `claude -p` lane passes `--agents <path>` directly.

What each launcher passes:
- `spawn_worker(role=)`: the context role (default GenericWorker); `extra_args` carries `--model` and `--effort`, and a Claude worker launch without both is refused. `tier` is gone and refuses any value. The render and the definitions are the ones of the cwd's profile; with no cwd, the worker home's.
- `spawn_child(context=, mode=, model=, effort=)`: the role, preset, model and effort of a child, on the parent's cwd and profile; `role=` is gone.
- `resume_worker(name, model=, effort=)`: replays the record's flags; a flag the record lacks comes from the call, and a resume without it is refused.
- Any other Claude worker launch with no system-prompt flag — a resume of a worker spawned before roles, the `assign-to-manager` relaunch — loads GenericWorker (a subworker: its `child` render) on the record's cwd.
- A pipeline node: `role`, `model` and `effort` in the schema. `model` is a `@<family>` token or a concrete `claude-<family>-<version>` id and `effort` one of `low`, `medium`, `high`, `xhigh`, `max`; the node launches with `--model` and `--effort` from them and reads no roster row. An optional `[nodes.<n>.model_when]` table (`input`, `line`, `equals`, `model`, `effort`, optional `unless`) launches the node on the rule's `model` and `effort` when the complete `input` record's first `<line>:` line starts with the word `equals` and no `unless` record is present in the current round; in every other case, a failed read included, the node keeps its own. Each `[nodes.<n>.subagents.<slot>]` names `type`, `model` and `effort`, and the node's agent guard denies an `Agent` call whose `subagent_type`, `model` and `effort` no entry names. Each child slot names its lanes (§ Lanes). A snapshot taken before roster-removal keeps `tier`, `tier_when` and `roles`; the engine reads them through the operator's legacy `~/.claude/dockwright-roster.toml` for one release (`dockwright doctor` `config:legacy-roster`); a fresh schema with any of them is refused.
- The manager: `manager_rc_args` adds the Manager render of the manager home's profile, its settings and its `--agents-file`. When the Manager role cannot load, the manager launches as before and prints why on stderr.
- Codex: a Codex worker gets `role.codex[.<profile>].md` in its bootstrap prompt, read from a prompt file; a `codex-exec` child gets it in its brief.
- A lane: `dockwright role-args <Role> --launch lane --cwd "$PWD" --base <settings>` prints the flags, one per line; `--render-only` prints the render pair alone, for a locked-down `claude -p` lane.

Two hooks watch the delivery. `SessionStart` warns a Claude session whose `claude` process carries no `--append-system-prompt-file` whose first line is a `<!-- dockwright-role:` marker, once `rules/no-role.md` exists; it denies nothing, and a Codex session gets `rules/no-role.md` itself through `AGENTS.md`. `SubagentStart` gives a subagent of a type that `[subagents]` does not build, other than `Explore` and `Plan`, a pointer at the `default_role` bundle of the session's profile.

`dockwright compose --check` also checks the roles: (a) a former rule neither in `rules/` nor named by a manifest; (b) a manifest skill in no place, a unit in two places; (c) a role fragment no manifest names; (d) a render missing, stale or unrenderable, or a drop-in that lands nowhere; (e) a tracked file of `~/.claude`, the canon (`[paths] dockwright_repo`) or the project layer citing a rule that moved out of `rules/` or a pool unit at its old flat path; (f) a render over its `[ceilings]` (a profile render's limit is the role's plus `profiles/<p>.md`); (g) with `[roles] strict`, a unit without frontmatter, or with a verb, domain or folder outside the vocabulary; (h) a file in `rules/` other than `no-role.md` once it exists; (i) two guards sharing a bind and a domain without `cites` (a warning); (j) a guard the baseline catalog names that left a role or a subagent without a `[[drop]]` in `roles/rulings.toml`; (k) a stale `roles/catalog.json`; (l) a flow section without a `Read by:` line (a warning) or naming a path that does not exist; (m) a render past its role's built-in size target (a warning).

With no manifest in the roles dir, every launcher builds the command it built before roles: `worker.md` appended, the manager reading `agents/manager.md`, a lane on its own `--settings`. Once any manifest exists, an unknown role, an undeclared launch or a missing render refuses the spawn. Three launchers fall back instead and launch without the role: the manager prints why on stderr, the gardener lane writes a `role` line to `gardener/run.log`, and a `claude -p` lane whose `role-args` call fails logs it and starts without the render.

## Hooks (in `~/.claude/settings.json`, Codex mirror in `~/.codex/hooks.json`)

Every dockwright hook is wrapped: `bash -c 'CLAUDE_PARENT_PID=$PPID dockwright <sub>'` — `$PPID` of the hook shell is claude's real PID, flowing into the active record so `kill_worker` targets the right process. Each hook gates on `CLAUDE_AGENT ∈ {manager, worker}` (plain sessions are no-ops) and short-circuits on the `CLAUDE_ORCHESTRATOR_DISTILL` sentinel (so headless distill children never register — that once caused infinite `claude -p` fan-out).

| Hook | What it does |
|---|---|
| `SessionStart` | Writes `active/<sid>.json` (resolves unique routing name; rolls a cosmetic `funny_name` for workers, a funny manager name if none pinned). Paints the tmux tab title: manager `🎯 <name> · <domain>`, worker `🔧 <funny> · <task>` (gray, or red if a pending question survived a resume). |
| `UserPromptSubmit` | Sets state=processing + stamps processing_since (tasking-episode bound for wait_for_worker's stale-done gating — covers re-tasks typed directly into the worker window); stamps `input_at` on every non-harness worker prompt (the question-mute and done-skip bound); paints worker tab busy. |
| `Stop` | Updates `last_summary` / `last_turn_at` from the transcript; sets `state=idle`; writes a turn-end marker into `turn-ends/<owning-manager>/`; paints tab gray (or red if a question is pending). Also stamps `last_turn_at_uptime` (awake clock: CLOCK_UPTIME_RAW on macOS, CLOCK_MONOTONIC on Linux) so idle math survives laptop sleep. |
| `SessionEnd` | Archives worker record to `closed/` (so `resume_worker` works), removes `active/`, drops the worker's pending questions. For managers: fallback distill to manager-memory if `/manager-close` didn't already write one. |
| `StopFailure` | On a turn an API error ended: writes the account's `model_spent` mark when the message is a model-limit banner on a worker or subworker. |
| `PostToolUse` (matcher `mcp__.*`) | Stores a `sent.chat` event for a call of a tool in `[events.sent] tools` whose response carries `message_context.message_ts` and `channel_id` (a listed tool without them stores `sent.unparsed`); exits silently on any other tool or session. Not installed in Codex mode. |

**Env contract** (stamped by the spawner / hook wrapper): `CLAUDE_AGENT`, `CLAUDE_WORKER_NAME`, `CLAUDE_PARENT_MANAGER`, `CLAUDE_PARENT_SID`, `CLAUDE_WORKER_KIND` (`subworker` on a worker's child; the spawner clears `CLAUDE_PARENT_PID`, `CLAUDE_DOMAIN`, `CLAUDE_ITERM_SID` for it), `CLAUDE_WORKER_PROVIDER` (headless providers only), `CLAUDE_WORKER_RUNTIME`, `CLAUDE_PARENT_PID`, `CLAUDE_DOMAIN`, `CLAUDE_ITERM_SID` (legacy name — now a tmux pane id). All are stripped (plus the `CLAUDE_ORCHESTRATOR_DISTILL` sentinel set) for distill children.

## Lane monitors

The dockwright plugin arms four lane monitors when a manager command invokes `Skill(dockwright:arm-lanes)` — `/manager`, `/manager-resume`, `/manager-takeover-recovery` and `/manager-reboot` all do. Each lane is one long-lived process running a one-shot CLI scan in a loop (identity — *which manager am I* — resolves per scan via `TMUX_PANE` → PPID-walk, so no name substitution into the command):

| Lane command | Cadence | Fires on |
|---|---|---|
| `dockwright monitor-loop pages` | 1s | prints every line waiting in `notify-outbox/<me>/`: Gardener digests, and with `[lanes] in_manager = false` every QUESTION, DONE, FINISHED_SILENTLY and stale-lane line the daemon wrote for you; prints `DAEMON_SILENT <min>min → dockwright daemon status` when the daemon has not stamped `daemon/alive.json` for 3 min of machine-awake time (ladder 10/20/40 min); prints `DAEMON_STUCK <step> <min>min → dockwright daemon status` when the stamp is fresh and one step has run over 10 min (same ladder) |
| `dockwright monitor-loop questions` | 2s | (in the tab only while `[lanes] in_manager = true`; otherwise the daemon does this scan and the row reads `IN-DAEMON`) new questions in `questions/<me>/` and my workers' `questions/by-task/<key>/`, each once → `QUESTION <worker> → … — <question>`. A legacy flat `questions/<id>.json` is not surfaced |
| `dockwright monitor-loop turn-ends` | 5s | (in the tab only while `[lanes] in_manager = true`; otherwise the daemon does this scan and the row reads `IN-DAEMON`) reads your workers' Stop-hook markers in `turn-ends/<me>/` and pings no turn-end on its own. It prints `FINISHED_SILENTLY <name>[ (session exited)] → … — <summary>` once a turn ended ≥30min ago (`CLAUDE_ORCH_SILENT_FINISH_GRACE_SEC`) and nothing suppresses it. Suppressed: a fresh done event from the current episode, another turn within the grace, a question asked since your last message or his typed line, your own turn-ends, nested records. Repeats per lull follow a doubling ladder (15/30/60min…, cap 4h); a re-instruction, a done event or session exit resets it. Holds while the session still runs a background shell, for the first 2h (`CLAUDE_ORCH_TURN_END_BUSY_SEC`), so a plannotator park stays silent. Parked worker paged: `~/.claude/agents/manager.md` § Design-gate relays |
| `dockwright monitor-loop done` | 2s | (in the tab only while `[lanes] in_manager = true`; otherwise the daemon does this scan and the row reads `IN-DAEMON`) new `done/<me>/` files → `DONE <worker> → … — <summary>`. `worker_done` writes `done/<parent-manager-name>/<sid>-<event_id>.json`, so only the owning manager is pinged; `done/_unscoped/` is never surfaced. A pipeline node whose own advance committed or whose fork row joined, and that holds no open request, prints nothing (a holder an override displaced, or whose advance was superseded, still prints): its done lands in the work's `events.jsonl` as a `lane_event`, and the done file stays. A done whose whole summary is one line that starts with `PARKED` and, with whitespace collapsed, equals the first line of the same session's previous done in `done/<me>/` prints nothing either. It lands in the work's `events.jsonl` as a `DONE` `lane_event` with `repeat`, the done file stays, and without the work's `events.jsonl` it prints. A done with a second line prints too, unless `worker_done` stamped it `engineer_input_at` and no `tasked_at` later than that previous done. The `/manager` boot sweep (`preflight_cleanup.py`) keeps the done files of sessions that still have an active record, so the previous done of a live parked node stays in `done/<me>/` past 24 h. `engineer_input_at` means the session's latest input was a line the engineer typed in its pane (`human_attached_at` equal to `input_at` on its active record). `tasked_at` is the last time a relay, a topic message or an engine wake was typed into it. Such a done lands in the journal the same way. |
| `dockwright monitor-loop stale` | 60s | (in the tab only while `[lanes] in_manager = true`; otherwise the daemon does this scan and the row reads `IN-DAEMON`) wraps `stale_monitor.py --manager <me>`: your own workers, your works' reconciler. The reconciler's kinds: `ADVANCE_STUCK` (the next node's spawn did not start), `ADVANCE_UNREGISTERED` (it started but the session never registered), `NODE_PARKED` (the holder was closed idle, or by a reboot; silent while the node's detached gate still runs), `NODE_UNADVANCED` (the holder died with its outputs complete and never advanced), `NODE_HELD` (you held the token and its holder is dead; once per hold; a work that will never run again: `pipeline_close`), `TRIGGER_POLL_FAILED` (`gh pr view` failed on a PR trigger edge, or the tracker read failed three times in a row on a status edge; see § Events), `RECONCILE_ERROR` (a reconcile pass raised), `MESSAGE_UNDELIVERED` (a `topic_message` record queued in `topic-outbox/` has reached no session for an hour; each pass retries your entries, and a dead manager's entries of your domain, every 5 min), `HANDED_OFF_CLOSED` (silent, journaled: `<task_key> <name> (done|grace|finished)` — the engine closed a node and its subworkers: `done` within a pass or two of its `worker_done` after the token left it, `grace` after `handed_off_grace_sec` with no report, `finished` for a terminal node (no edge out of it: `ship-internal`, `close`, `resolved`, `intake`, `verify`, `ticket-draft`; a node whose only edge out is a status trigger is not terminal: the trigger moves it) whose outputs are complete and reported, on the token's first entry onto that node in the round only: a re-entered terminal node waits for the 2 h idle reaper, and in a later round an override onto a terminal node whose complete output the rework carried over finishes the holder on that output once it reports; an open gate, a pending question and his attachment hold a node open). `LIMIT_CLEARED` means you yourself sat on a limit banner: your question, done and turn-end events were held while you were down and replay after that rollup line |

The loop ends rather than scanning on forever, and the harness reports its exit as `Monitor "dockwright <lane> lane" script failed (exit N)`. A scan exiting `2` — the owning manager cannot be resolved — does NOT end the lane at once: the loop keeps retrying for a 600 s grace (`CLAUDE_ORCH_LANE_RESOLVE_GRACE_SEC`, its own interval for the first minute, then every 15 s), which is what carries a lane across a `/clear`. The loop's own exit codes:

| exit | constant (`lane_io`) | cause | what you do |
|---|---|---|---|
| 2 | — | usage: unknown lane name | broken deploy — `setup.sh` |
| 3 | `EXIT_LANE_DEAD` | the stdout reader is gone | the session is going away; nothing |
| 4 | `EXIT_LANE_WEDGED` | scans failed `max_consecutive_errors` times in a row | fallback or a fresh tab |

**`dockwright lanes [manager-name]`** answers "are my lanes still delivering?" — one row per lane (`OK` / `BACKLOGGED` / `ARMED-UNRESOLVED` / `STALLED` / `HUNG` / `DEAD` / `NEVER-ARMED`), non-zero exit if any lane is not OK. It reads a per-lane heartbeat that a scan writes only after proving it could still reach its reader, cross-checked against unconsumed events on disk and against the lane's own marker under `lanes/<cli_pid>/`. `turn-ends` and `stale` report `backlog=n/a` — both legitimately hold events, so counting one would cry wolf. It prints a recovery line under every non-OK row; a lane that died cannot be re-armed by the plugin in the same CLI process — the line names the fallback. `HUNG` reads the marker's `last_iter`: a live lane process that has not completed an iteration for its own window still holds the lane lock, so its line names the `kill` first and the fallback second.

Every lane line reads `KIND <fields> → <step>` and, when there is one, ` — <tail>`: the step is the manager's next call, written with the tool names the manager core uses, and it comes before the tail because the harness cuts an event line at 500 characters. A kind with no manager action does not print. The silent kinds are `ADVANCE_RECONCILED`, `NODE_RESTARTED`, `ADVANCE_SETTLED` and `TRIGGER_FIRED` (the engine already journals each), `TRIGGER_WAKE`, `EVENT_WAKE`, `LEASE_WAKE`, `HANDED_OFF_CLOSED` and `NODE_NO_SUMMARY` (one `lane_event` each in the work's `events.jsonl`), a pipeline node's `DONE` after its advance committed or when it repeats its previous `PARKED` line bare or while the engineer's own line is the latest input at its pane and no relay started a wake since the previous done, and on the stale lane a first `NUDGED`, a worker's limit-reset `NUDGED`, the manager's own limit-reset `NUDGED`, `RESUMED`, a worker's 70 % `CONTEXT`, `IDLE_NUDGED`, `MODEL_FALLBACK` and `ORPHANED_CHILD`. A silent stale-lane kind lands as a `lane_event` only for a worker whose assignment carries a `ticket` whose `artifacts/<ticket>/events.jsonl` already exists; other workers' silent lines go nowhere. `lane_event` and `message_delivered` are reserved event types: `pipeline_event` refuses them and the engine's fold skips them. `stale_monitor.py` emits edge-triggered alarms — `STALE_PROCESSING <name> (<m>min)` (a processing worker's transcript silent past 30min, re-paged at 60/120…; transcript-activity age, else turn age). The page is skipped while the worker's own pending question was asked at or after its latest input (`tasked_at`, `input_at`) and no credit, Fable or safeguard action was held for it, and fires at the current step on the first pass after the answer or a new input. With `CLAUDE_ORCH_AUTONUDGE=1` the lane types "resume your task" instead, on a 30/60/120min ladder: the first `NUDGED` is silent, a `NUDGED` whose previous nudge got no activity since wakes you, and the next one after a silent `RESUMED` (the transcript grew after a nudge: any activity, a submitted manager message included) is silent again. A worker's `NUDGED <name> (limit-reset)` fires at the banner's parsed reset time +2min on the schedule a rate-limited nudge set, so it is silent; a still-stuck worker wakes you on the next ladder nudge. `CONTEXT` pages each crossing of 70/80/90 % of that session's window once; dropping under a step re-arms it. `LANE_SILENT <lane>` comes from the stale lane checking its peers' heartbeats every 60s; it repeats on a ladder (10/20/40min…, cap 4h) and clears on recovery. Workers idle >2h with no pending question and no live model-credit banner get auto-closed (a credit-dead worker is held out of the reaper for as long as the banner stands, so it must be switched by hand or closed) (archived to `closed/`, pane gracefully closed so SessionEnd fires; threshold via `CLAUDE_ORCH_IDLE_TTL_HOURS`), silently: the stale lane prints no line for it. Gardener lines are diverted to a per-manager notify-outbox and ride the next wake from any monitor lane (or flush within 30min) instead of paging on their own; an entry's `source` is its urgency class: `daemon` and `board` entries flush on the next pages pass, any other source waits for one of them or 30 minutes; `ORPHANED_CHILD` is silent and no longer goes there. `MODEL_FALLBACK <name>` / `MODEL_CREDIT_EXHAUSTED <name>` cover a per-model credit banner, which bricks nothing and must not flip the account: on any claude worker whose last assistant EVENT is that CLI error — whatever its `state`, because the check runs before the lane branches on `state` and a credit-exhausted turn never ends and so never reaches `idle` — the lane types `/model` + `/effort` (`CLAUDE_ORCH_MODEL_FALLBACK`, `CLAUDE_ORCH_MODEL_FALLBACK_EFFORT`) and a resume nudge, once, then re-checks after `CLAUDE_ORCH_MODEL_FALLBACK_CONFIRM_SEC` (600s) and pages if the banner is still there. It draws from the same per-scan send budget as the idle nudge, but ONE unit buys THREE pastes here, so three firing workers cost 3 units and 9 pastes; size a burst from all three ladders and price this one at 3x. A MANAGER whose turn ends on the same banner gets three pastes of its own into its own pane, and all three differ from a worker's. The manager lane rescues onto the `@opus[1m]` token, which keeps the 1M window a manager's context needs, and a takeover manager launches on it too; the worker lane rescues onto the `@sonnet` row. The worker target is an EMERGENCY one, not a judgement about the tier the work deserves: a rescued worker is expected to finish the task in hand and be re-spawned, never to keep running there. ⛔ A rescue is REFUSED, not typed, when the target is the same model FAMILY the session just spent — the lane reads the family out of the banner and compares it to the target, so a bare id and its `[1m]` variant count as one — and it pages `MODEL_CREDIT_EXHAUSTED … no rescue target is left` on the spot instead of typing a no-op and discovering it 600s later. The lane resolves both sides to concrete ids before comparing, so a token never reaches that comparison. Expect that whenever your own sessions run a fallback's own family: point `CLAUDE_ORCH_MODEL_FALLBACK` (and `CLAUDE_ORCH_MODEL_FALLBACK_EFFORT`) at a family you still have credits on; those two retune workers only. The 600s re-check still pages `MODEL_CREDIT_EXHAUSTED … the fallback itself is out` for a rescue that WAS typed and did not take. ⛔ The effort is `MANAGER_MODEL_FALLBACK_EFFORT`, a hardcoded `xhigh`, the effort paired with Opus — `CLAUDE_ORCH_MODEL_FALLBACK_EFFORT` does NOT reach it, so setting that variable retunes workers only. The third is a resume-orchestration line that names the typed model and says the banner is about that session's model, not the workers'. All of it sits outside that budget; it never flips the account and never launches a recovery tab, because a credit banner bricks no account. `IDLE_NUDGED <name>` / `IDLE_UNTASKED <name>` close the gap between a worker's last turn and that autoclose: a worker sitting `idle` past `CLAUDE_ORCH_IDLE_UNTASKED_MIN` (45min of machine-AWAKE time, same clock as the autoclose, so it understates wall time across a laptop sleep) with nobody having re-tasked it gets `resume-or-finish` typed into its pane as a silent `IDLE_NUDGED`, and an `IDLE_UNTASKED` page reaches the manager when nothing could be typed. It fires once per stall — the key is the worker, not the turn, so a worker that answers the nudge and stops again types nothing more. A new stall starts when the manager re-tasks the worker (`tasked_at`), or when any prompt, a harness notification included, starts a turn more than 2 minutes after the nudge (`processing_since`, `CLAUDE_ORCH_TURN_END_GRACE_SEC`). `tasked_at` re-arms with no delay: a send whose text never reached the CLI still counts, so a second nudge can follow the first within minutes. Each re-arm costs a manager send or a new turn, so it cannot run away. At most `CLAUDE_ORCH_IDLE_UNTASKED_MAX_SENDS` (3) IDLE_NUDGED wakes are typed per scan — the rest keep no state and are reconsidered 60s later, so a backlog of nine drains in about two minutes instead of waking every worker at once; `IDLE_UNTASKED` pages are not capped. ⛔ That bound covers THIS signal only: `NUDGED` from the processing branch is a separate ladder with no cap, so a single scan can type into more panes than this number — measured at 5 with three idle wakes and two `NUDGED`. Size a burst from both, not from this alone. A worker sitting on the credit banner leaves that `NUDGED` ladder: it is never typed a bare resume onto a model that is out of credits, and its switch draws from the capped budget above. A SUBWORKER is never typed the switch at all — its pane runs a one-shot `claude -p` / `codex exec`, where `/model` is text appended to a process that will not read it. On a FABLE banner no older than the session's launch the lane does not switch in place when another account still has Fable: it closes the worker's window, waits for its process to exit, archives it (`closed_reason: "fable-moved"`, or `moved: "fable"` on a record SessionEnd wrote) and resumes it through the manager's auto-send (`resume_worker` lands it on an account with Fable left, or on Opus at `xhigh`); it switches to Opus in place only when no account has Fable left, and closes an interactive subworker with `closed_reason: "fable-spent"` so its parent re-dispatches the round. `FABLE_LIMIT` is silent on a move and pages `resume-refused` after three refused resumes, `close-refused` when the process outlives the window close by 15 s, `human` when the resumed pane is human-attached, `unsent-text` when text sits unsubmitted in the pane (clear the line; the lane moves it on a later tick), and `not-typed` with autonudge off, a human at the pane, or the standalone copy of the monitor; a `paged` move pages again whenever its page key is lost, and a page carried through a manager's limited stretch is replayed to the recovery tab after `LIMIT_CLEARED`. The move state lives under `fable-move:<sid>:<started_at>` in the emitted state, so a resumed session (a new `started_at`) is never blocked by its predecessor's record. Suppressed while a question is pending, while the worker's latest `worker_done` is newer than its last non-harness input (`max(tasked_at, input_at)`), while the transcript or a subagent is live, while the session sits on a limit banner, and while the worker holds a live background shell (a human review gate or a long command) until `CLAUDE_ORCH_IDLE_UNTASKED_BUSY_MIN` (120min). `CLAUDE_ORCH_IDLE_UNTASKED_MIN` must stay above the `FINISHED_SILENTLY` grace (`CLAUDE_ORCH_SILENT_FINISH_GRACE_SEC`, 30 min), otherwise the nudge's turn supersedes the turn-end and `FINISHED_SILENTLY` never pages. ⚠️ **The typed nudge is gated on `CLAUDE_ORCH_AUTONUDGE=1`, which defaults OFF in code** — unset, you get the `IDLE_UNTASKED` page and nothing is typed. The gate is an environment variable, so two operators on the same version can see different behaviour with nothing in the source to explain it. ⛔ Check it, do not assume: it is inherited from the **tmux server's global environment** (`tmux -L dockwright show-environment -g | grep AUTONUDGE`), which every session in that server picks up and which survives manager restarts — so "I launched this manager from a clean shell" does not mean the nudge is off. Under the daemon ([lanes] in_manager = false) the knob comes from `[lanes.env]` in dockwright.toml, copied into the launchd plists by `dockwright daemon sync`; `dockwright doctor` (lanes:env) flags a tmux value the table lacks. The same variable also gates the bootlite watchdog's orphan nudge, a different loop with different text. Before typing an idle nudge or autoclosing, the monitor captures the pane and holds when it shows the CLI's spinner line (`Thinking… (10m 25s …)`) — a live turn the record's `state` missed after a context compaction. `preflight_cleanup.py` runs at `/manager` boot: prunes aborted handoffs (>1h unconsumed), consumed handoffs + turn-end events (>24h), done events (>24h) of sessions with no active record, closed records (>7d), dead-pid active records, and `lanes/<cli_pid>/` marker directories of dead CLI pids.

## Events

A node that waits on something outside the fleet subscribes and parks; the engine polls and wakes it with one pane line `event: <source>.<kind> — <text>` (`via: reconcile`, `decided_by: manager`, ranks in no decision tier). The old `trigger: …` and `lease: free — …` records are read for one release.

A source stores events and a rule reacts to them: a design keeps storing and reacting apart.

- **Trigger edges.** An edge carries `trigger = "merge"` or `trigger = "approve"`; `validate` refuses `approve` unless the target declares the checkpoint `merge.state`. The stale lane polls every PR URL of the source's `implement.*` outputs once per `[pipeline] trigger_poll_sec` (`gh pr view --json` with state, merge, review, head, checks and author fields) into one line per PR: `<owner/repo#n> <phase> <head7> <reviewDecision|-> <mergeStateStatus|-> <checks> <review|->`, the phase `merged`, `closed`, `conflict`, `changes`, `ready` or `open`, the review the latest `submittedAt` not by the author. `merge` fires once every PR has `mergedAt`; `approve` fires when a PR ended later than the token's entry into the source, or every PR ended, or the first unmerged PR in line order is `ready`, and the source holder is idle or gone; `trigger_fired` carries the observation, but its review column counts as delivered only as far as an `event: github.` record written since the source's entry carried it (none: the entry). In the pass that fires `approve`, a review newer than that mark and quiet for `[pipeline] review_quiet_sec` goes to the new holder as `event: github.pr — <observation>`. An idle or gone source holder gets `event: github.conflict — <observation>` for a conflict on a head the last `event: github.` record since the entry did not show, and `event: github.review — <observation>` for a review newer than that record (no record: than the entry) and quiet for `[pipeline] review_quiet_sec` (1800); either restarts a finished holder. While the target's `merge.state` starts with `waiting`, the lane delivers `event: github.pr — <observation>` when a column other than the review differs from the last delivered observation, or when a review newer than the last delivered one (or than the fire's mark) has been quiet for `review_quiet_sec`. `trigger_heartbeat_sec` is 0 by default: no clock wake unless set. A dead waiting target is only woken; `pipeline_status` shows `external:merge`. A third kind, `trigger = "status"` with `status = ["<name>", "category:<key>", …]`, is read by the stale lane once per `trigger_poll_sec` from the tracker (`GET /rest/api/3/issue/<task_key>?fields=status`; a task key that is not a tracker key never fires) and moves the token when the status name, or `category:<statusCategory.key>`, is listed, the holder is idle or gone, the work has no open request or pending question, and the edge's `exit_checks` pass; `trigger_fired` carries `tracker status <name> (<category>)`. A failed read pages `TRIGGER_POLL_FAILED` only after 3 failures in a row over 10 minutes of machine-awake time, a read the machine slept through not counting, then once an hour; a successful read clears the count.
- **Subscriptions.** `event_subscribe(claude_sid, task_key, node, source, match, kinds?, after?, deadline?, handler?, skip_own?)` or `dockwright event subscribe --task-key K --node N --source tracker|deploy|time|chat --match k=v … [--kinds a,b] [--after X] [--deadline TS] [--skip-own ID] [--handler "<argv>"]`: `tracker` comments and status of `issue=<KEY>` (`after` required), `deploy` the Actions deploy job of `repo=<o/r> env=staging|dev|prod sha=<sha40>|run_id=<id>` (prod: GitHub Deployments of `[events.sources.github] deployed_envs`, sha only, `success` only), `time` a deadline alone, `chat` a chat app's messages (`app`, `conversation`, `sender`, `channel`, `thread`; kinds `dm`, `channel`, `dm-thread`, `channel-thread`; no `after`). Only the token holder subscribes, on its own node; a fork row cannot; a repeat with the same (task_key, node, source, match) replaces (a `chat` repeat keeps the earlier window and delivered mark); the layer off refuses (CLI exit 3). The daemon pass and the stale lane poll each source on `[events.sources.<name>] every_sec` while a subscription or an enabled rule names it, each source on its own thread under `events/cursors/<name>/.poll.lock` (held by another process: the source skips the pass, `events_poll_busy`), append its batch to `events/log/<day>.jsonl` in `(ts, id)` order and move the cursor after a clean poll. The step waits for every source, then runs the rules under `events/.rules.lock` (held: `events_rules_busy`). The reconciler wakes the idle or dead holder once per pass with every new event, `event: <source>.<kind> — <summary> (sub <id>)` joined by ` · `, a freed lease on the same line as `event: lease.free — <category>`, journals `EVENT_WAKE` and marks them delivered. A `deploy.job` or `time.deadline` wake ends its subscription; the token leaving, `topic close`, `pipeline_close` and a finished holder drop the rest. A `handler` (its argv starts with an entry of `[events] handlers`, a name or a name with the leading arguments it pins, found in `handler_path`) runs first, 60 s, the batch as JSON on stdin, only its source's variables: exit 0 handles with no wake, any other exit wakes with `(handler failed: <code>)`. A `tracker` subscription that reads status gets the current status as its first status event, so a Done reached before the first poll still fires. A deploy event belongs to one subscription (`sub_id` in its match); a new subscription on the same sha polls again. One failing issue or run is recorded in the source's cursor (`failed`), paged once an hour, and polled last next pass while the others poll; a call that runs past the 30 s budget is retried first next pass. `pipeline_status` shows `external:<source>`; a parked subscribed holder gets no `NODE_PARKED`.
- **Pages.** `EVENT_POLL_FAILED <source>` (cursor unchanged and the item retried; paged only after the same item, or the whole source, failed 3 polls in a row over at least 10 minutes of machine-awake time: a poll the machine slept through does not count, and a failure that recovers first pages nothing and leaves `held` on its `events_poll_failed` record in `daemon/ledger.jsonl` while `[lanes] in_manager = false` (with `true`, only its count in `events/cursors/<name>/failures.json` while the streak lasts); with `skipped`, notifications the `chat` source could not read, not retried, paged at once; once an hour), `EVENT_ENV_INSECURE <path> <reason>` (`[events] env_file` missing or not mode 0600; tracker idles), `EVENT_STARTED <key> <rule>` (a rule started a work under you), `EVENT_PAGE <rule>` (a `page` rule's event, to the live manager of its domain), `EVENT_QUEUE <rule>` (a `queue` rule's reminder to the live manager of its domain: `<n> pending, oldest <summary>`; `event_queue(rule)` lists them oldest first and `event_ack(rule, event_id | "*")` closes them; repeats every `nudge_sec` while the queue is not empty), `EVENT_STALLED <rule> <domain>` (no live manager of the domain), `EVENT_RULE_FAILED <rule>` (the rule raised, the other rules ran, and it retries from its cursor next pass; once an hour per rule), `CHAT_ARCHIVE_FAILED <auth|http|parser|hand|crash> → <failure>; see dockwright chat-archive status` (the chat archive's pass failed: `http`, `hand` and an `auth` whose text starts with `keychain:` page after 3 failed passes in a row over at least 10 minutes of machine-awake time, a pass the machine slept through not counting, a failure that recovers first pages nothing and leaves `held` in `chat/ledger.jsonl`, and only a full pass that runs every step and leaves no failing trigger untried clears a count; any other `auth`, `parser` and `crash` page on the pass they happen; once an hour per kind; fix: read that status, then `dockwright doctor`; an `auth` whose text starts with `keychain:` is the Keychain, not the token: unlock it, or under launchd set `runner = "manager"`; any other `auth` means every account's token got a 401 and the hourly nudge did not recover one: re-authenticate with `/mcp` in a session on the default account, the one whose Keychain item `[chat_archive] keychain_service` names: start it with `env -u CLAUDE_CONFIG_DIR claude`; `crash` names the step and the exception class of a failure the pass did not expect: the step rolled back and the others ran). `doctor` checks the env file, the rules, subscriptions left while the layer is off, and the `[chat_archive]` section with its ledger.
- **Rules.** `[events.rules.<name>]` (`source`, `kind`, `action = start|page|queue|reply`, `schema`, `domain`, `max_open` = 2, `types`, `skip_status`, `enabled`, `match`, `stop_file`, `while`, `nudge_sec` = 600, `on_change`, `repeat_sec`, `repeat_values`, `confirm_events` = 1, `unless_rules`, `ack_sec` = 600, `inbound`, `inbound_skip_senders` (all four reply only; an error on any other action; `inbound` needs kind `dm` or `dm-thread`, and `inbound_skip_senders` needs `inbound = true`)): a `start` rule begins a work of `schema` keyed by the issue under the live manager of `domain` from each new event while fewer than `max_open` of its works hold a slot, and pages `EVENT_STARTED`; its works are the ones it started and, for the tracker sprint rule, every work on an issue the latest sprint search found; a work holds its slot while it has an open request, its schema or log does not load, a question waits on it, or a token the manager does not hold (each row of a fork on its own) reads `worker:*`, `stalled:*`, `human:question` or `human:approval-dialog`, and frees it once closed, or once each of its tokens is held by the manager or reads `human:gate`, `none` or an `external:*` value; a start the engine refuses takes no slot; `page` pages the domain manager with `EVENT_PAGE` and stalls like `start` without one; of several pending events of one wait (same kind, match and cursor key, as a github ping repeated through a stall) it pages the newest only and moves its cursor past the rest. `queue` stores each event in `events/queues/<name>.json` and reminds the live manager of `domain` with `EVENT_QUEUE` on a new event and every `nudge_sec` until `event_ack` closes it; without a manager it stalls like `start`, and the queue keeps filling. `match` passes only events whose match fields equal it; while `stop_file` exists, or while `while` (the exec command's shape, `{ kind, match }`) is set and no stored exec window of that kind covers now, the rule moves its cursor and queues, pages or starts nothing; inside its window a `queue` rule with `while` queues only events whose own time (`payload.delivered` when it is a number, else `ts`) is at or after the window's start, and before it reminds it drops each queued record whose own time is earlier (`event_queue_dropped {rule, count, reason: window}`, ledger only). The window's start is the start of the unbroken coverage inside the newest set: from the earliest window that covers now, it steps back through the set's windows that start earlier and reach it, so a split shift keeps its first start; earlier sets never move it, and a window a command re-issues with a new start on every read moves it each time. `dockwright event gate <rule>` exits 0 while the rule acts (its line carries that `start`, unix seconds, for a rule with `while`) and 1 with the reason (`disabled`, `error`, `stop_file`, `window`) while it does not. A rule seen for the first time starts its cursor at now. Each rule runs on its own: one that raises keeps what it recorded before, records `event_rule_failed`, and the other rules run. `on_change` (queue rules only) queues an event when its match value differs from the last queued one, or again after `repeat_sec` for a value in `repeat_values` (empty: any value). `confirm_events` queues a changed value only once that many consecutive events of the rule carry it. The sprint search runs on a tracker poll at most every `[events.sources.tracker] sprint_every_sec` (1200), and on the next tracker poll after a failure or a spent budget; issue comments and status keep `every_sec`. The tracker sprint search seeds its cursor on the first pass and emits `tracker.sprint-assigned` for new keys after it: a sub-task of yours alone (`parent` in the payload) while its parent is not yours or another sub-task of the parent is someone else's or open and unassigned, else the parent once (`subtasks` in the payload); `types` and `skip_status` test a sub-task by its parent, and a key a started parent or sub-task covers never starts again. Before a sprint start, the rule reads the status of the issue and of each `subtasks` key from the tracker and skips the event (`<key> is past To Do`, `<key> is in <status>`, `<key> was not found`) when the issue is gone, outside the To Do status category or in `skip_status`, or a sub-task is outside the To Do category and not in `skip_status`; a sub-task that starts alone is tested on itself; a failed read, or an env file that does not load, holds the event to the next pass. A `start` rule skips (`event_rule_skipped`) an event whose `parent` or `subtasks` key has a work not closed by `pipeline_close`, one at a gate included. The skip goes only to the daemon ledger, and the other sub-tasks of a skipped parent never start by rule: start them by hand. `event_queue` and `event_ack` take a `queue` or a `reply` rule; `event_ack` refuses `"*"` on a `reply` rule.
- **sent source.** Written by the post-tool-use hook, never polled; kinds `chat` (`match`: `channel`, `thread`, `sid`, `name`, `agent`, `domain`, `tool`; `cursor_key` the exact message ts; `payload`: `to`, `link`, `text` (200 chars), `thread_ts`) and `unparsed` (`match`: `sid`, `name`, `tool`; the response head in `summary`). `[events] retention_days` (14) bounds every source's day files: the events step deletes `events/log/<day>.jsonl` older than it once an hour from either caller (the daemon pass and the manager's stale lane) and the read window and the dedup follow it.
- **reply action.** For each new `chat` event of the rule's kind with a `channel`: an event an enabled rule of `unless_rules` that is not off (its `stop_file`, its `while`) also matches is left to it, unless that queue rule's `while` keeps it out by its own time; the newest `sent.chat` of the same conversation (`dm`: a top-level record) or thread (`-thread`: the record's ts or its thread) before the message is the sender; without one, while `[chat_archive] sent_footer` and `self_user_id` are set, our newest message with the footer in `chat/archive.db` stands in (`sender_name = a session (footer match)`, domain general); a `dm` after one of his own unsigned messages between our send and the reply wakes nobody. Each such event becomes one record in the rule's queue before the cursor moves (`event_reply_queued {rule, event_id, inbound, channel, thread, msg_ts}` in the ledger): `summary` = `<sender> replied in <conversation> (<channel>[, thread <ts>]) to <name>'s message of <ts>: chat_read(conversation="<channel>", after="<ts>")`, and `payload.reply` = `channel`, `thread`, `sent_ts`, `sender_name`, `sender_sid` (the live session's sid after a rotation), `sender_agent`, `sender_pid`, `domain`, `link`, `text` (the line with its conduct tail), `msg_ts`, `sender_id`, `inbound`, `queued_at`, `delivered_at`, `delivered_sid`, `escalated_at`. While the sender is a live worker (by sid, or by name and pid after a sid rotation), each pass types one pane line `event: sent.reply — <the line> — read it …` per worker, conversation and thread for the records it has not received: the tail names the rule, the id of every such record and the address `<rule> <event id> <channel> <thread or -> <msg ts>` of the newest. A line that lands (`reply_policy`: an idle or queued input line; idle only with a human attached) stamps `delivered_at` and `delivered_sid` and writes one `event_reply_wake` per record; a line that does not land is typed again on the next pass, until the records ripen. The worker's `event_ack(rule, id)` closes a record. A record with no ack ripens `ack_sec` after `delivered_at`, or after `queued_at` when no line landed; a reply to a dead session or to a manager's own message ripens the same way, and a record an older daemon queued ripens at once. A ripe record gets `escalated_at` and the id `<id>:esc` (`event_reply_escalated {rule, event_id, new_event_id}`), so `event_ack` of the old id returns `removed: 0`, and it gets no further pane line. `EVENT_QUEUE <rule>` then reminds the live manager of each sender domain, in that pass and every `nudge_sec`, with the count of its escalated records; a domain without a manager stalls the rule (`EVENT_STALLED`, hourly) while the others are reminded. An escalated record whose `channel` and `msg_ts` an open `ask_engineer` question names in a first line `dm-reply: <rule> <event id> <channel> <thread or -> <msg ts>` is not counted and reminds nobody. `inbound = true` also queues an event of a one-to-one conversation (`channel` starts with `D`) that has no sender of ours, or that follows his own unsigned message, as a record with `inbound: true`, empty sender fields, the rule's `domain` and `summary` = `<sender> wrote in <conversation> (<channel>[, thread <ts>]) with no message of ours before it: chat_read(…)`; it gets no pane line and ripens `ack_sec` after `queued_at`. While `[chat_archive] sent_footer` and `self_user_id` are set, a ripe or escalated top-level record of a `D` conversation with a `msg_ts` is dropped (`event_reply_dropped {rule, event_id, reason}`) when its `sender_id` is in `inbound_skip_senders` (`skip`) or the archive holds an unsigned message of his after it (`answered`), except a record its live worker has not received. The archive holds a thread reply only once its pass has read the thread: a DM-thread reply reaches `chat_read` on the next full pass, and an untracked channel thread only through the footer route above.
- **github source.** Rules only (no subscriptions); kinds `review-wait` (an open non-draft PR of the configured owners' login without a human review for `review_after_hours` business hours) and `approval-wait` (a waiting Actions run that contains the login's latest merge into a repo and whose code is not yet on a `deployed_envs` environment, for `approval_after_hours` business hours); a run waiting only on a `fallback_envs` environment pages only when at least one job matches `fallback_skipped_job` and every job matching it ended `skipped`; every threshold, owner list and environment list is a `[events.sources.github]` key; polled only while an enabled rule names it; a repeat event every `repeat_hours` business hours while the wait goes on, each with its ping number in the id.
- **chat source.** macOS only. `[events.sources.chat] apps` names the app bundle ids to read; `every_sec` is 30; the daemon never contacts the app. While `[chat_archive] enabled = true` the source is polled with or without a subscription, and each poll reads `chat/archive.db` read-only for the rows of `messages` and `resolved` captured since its cursor (`archive` = `{messages, resolved}`, the largest `captured_at` and `resolved_at` it has read, both read inclusive; a cursor without it starts at the archive's last pass). Each archived message of a person gives one event, with or without a notification: id `chat:msg:<conversation id>:<ts>`, kind `channel` or `dm` (a group conversation is `dm`) with `-thread` on a reply in a thread, `channel` (the conversation id), `thread` (the parent ts), `payload.ref = archive_<ts>`, `payload.scout = "ok"`, `sender_id` and `link`; `conversation` is `#<name>` for a channel (private ones included), the other person's name for a direct message and the member list for a group, and `sender` is the message's sender. No archive event comes from a message whose sender is `[chat_archive] self_user_id`, from a bot (a sender id that starts with `B`, or a sender with any archived row marked as a bot) or from a message older than `[events] retention_days`; a message that already has an event in `events/log` gets no second one. The wake line carries the ids: `event: chat.channel-thread — <sender> in #<name> · thread <parent ts> · channel <id> · ref archive_<ts>`, kept ahead of the 200-character cut. The system notification store is read read-only as the archive's trigger and as the banner path: every new row delivered after the archive's `chat/started` mark gets a trigger file `chat/triggers/<key>.json` (the row's ids, time and subtitle, never text), which wakes the archive's launchd agent within seconds, and while a row waits the daemon toggles `chat/triggers/.wake` so the agent retries the trigger. A row whose message has an archive event leaves with no event of its own; a row whose message has no archive event for 300 s gives a banner event `chat:<key>`, a `dm`/`channel` event classed from the banner text without `channel` and `thread` (`payload.scout = "not in archive"`, `ref` = the app's notification id); that is a message the archive does not hold, and also a notified message of a bot, which the archive holds, and the archive event still follows as a second event if the message is archived later (a name-based subscriber wakes twice). While the archive is off, or `[chat_archive] self_user_id` is empty, no archive is read and every row gives its banner event at once (`payload.scout = "off"`); coverage is then only what the app delivered as a notification, and `doctor` (`chat-archive:config`) fails on an empty `self_user_id` while the archive is enabled. An unreadable `archive.db` gives no archive events for that poll and keeps the cursor. The event carries no message text: the woken node reads the thread with the `channel` and `thread` ids of its wake line in one call (`chat_read(after=…, thread=<parent ts>)` from the archive, or the app's MCP). An unreadable store pages `EVENT_POLL_FAILED chat` after 3 failed polls in a row over 10 minutes of machine-awake time: a missing store names its path, and a refused read names who needs Full Disk Access, the daemon's interpreter or, with `[lanes] in_manager = true`, the terminal app the manager runs in; archive events wait and go out on the first poll that reads the store again. A notification it cannot decode is skipped and paged as skipped at once, on its own hourly throttle. An event's `ts` is the poll that built it, and its `cursor_key` is the message's own time (the notification's for a banner event). A subscription's `after` is set to its subscription time, so it wakes only on messages sent after it subscribed, also after a gap with no subscription.
- **exec source.** Rules only; `[[events.sources.exec.commands]]` names argv lists the daemon runs on each command's `every_sec` (120) while an enabled rule names the source, skipping a command whose `stop_file` exists or whose `while` names a kind with no stored window covering now; each non-empty stdout line is a JSON object `{id, kind, match?, summary?, payload?}` and becomes an `exec.<kind>` event with id `exec:<id>`; a non-zero exit, a timeout or a malformed line keeps the valid lines as events and pages `EVENT_POLL_FAILED exec` after 3 failed runs of the same command in a row over 10 minutes of machine-awake time, then once an hour; a poll that does not run the command neither counts nor clears its streak.
- **chat archive.** A background pass (`dockwright chat-archive pass`, the `<prefix>.chat-archive` launchd agent every 300 s and on a trigger file, or the manager's `chat-archive loop` monitor with `runner = "manager"`) keeps the operator's direct messages, group conversations and the whole threads that mention them (every key of `mention_keys`) on disk under `<state_root>/chat/` for `retention_days` (90): `archive.db` (SQLite with FTS5), `raw/<day>.jsonl` (the responses as they came), `ledger.jsonl` (one record per pass). It reads through `chat_read(after, before, conversation, thread, bots, limit)` (grouped by conversation; every answer carries `archive`: `ok`, `off` while `enabled` is false, `empty` before the first message, `stale` when a search step of the pass (`dm`, `threads`, a `mention:<key>`) has not committed within max(15 minutes, 3 × `every_sec`), and `since`, the archive's start, before which it holds nothing), `chat_search(query, …)` (FTS5, bm25) and `chat_conversations(kind, since)` on the dockwright MCP, and `dockwright chat-archive read | search | conversations | status | reindex` on the CLI. The chat source reads it on every poll and builds the chat events from its rows. A thread of a channel the archive does not track also joins it when a notification resolves a reply in it and the thread holds a message of ours that ends with `[chat_archive] sent_footer`: the pass reads the thread once, stores it only on that match, and tracks it from then on; with `sent_footer` empty the thread stays out. `[chat_archive]` keys: `enabled`, `hand` (`direct`: the app's MCP over HTTP with the freshest OAuth token, by `expiresAt`, that Claude Code keeps in the Keychain for an account of `[accounts] pool`: the item `keychain_service` for the default account, `keychain_service-<first 8 hex digits of the sha256 of the account's config dir>` for each other; on a 401 it re-reads every item and retries with the freshest untried token, and only after every token got a 401 does it run the nudge, at most once an hour; every account's grant must belong to the same chat user; `claude`: a headless `claude -p` on `model` pressing the same read tools), `runner` (`launchd` or `manager`), `mcp_url`, `mcp_server`, `keychain_service`, `model`, `self_user_id`, `mention_keys` (empty: `[self_user_id]`), `retention_days`, `every_sec`, `group_sweep_sec`, `registry_sec`, `search_overlap_sec`, `write_tools`, and `[chat_archive.tools]` `search`, `read_conversation`, `read_thread`, `list_conversations`; `enabled` is forced off while a required key is empty, and `doctor` (`chat-archive:config`) names the missing one, a stale ledger and the last pass's errors. `dockwright chat-archive status` shows the ledger age, counts, cursors, pending and dead triggers, parser misses, the Keychain entry and the account the last pass used, and `auth_retries_24h`. Widening what it keeps is the operator's call, never a design default.
- **Leases.** A node that got `acquired: false` from `acquire_worker_slot(..., task_key, node, wait=False)` waits on the category; once it frees, the wake above reaches the idle or dead holder of that node and the waiter is dropped; a waiter of a node the token left is dropped silently. `[pipeline] lease_ttl_sec` (7200) is the expiry.

## Flows

### F1. Spawn
Manager calls `spawn_worker(name="rebase-bot", initial_prompt=…, extra_args=["--model", "@opus[1m]", "--effort", "xhigh"], manager_sid=<own sid>)` → spawner opens a window in the `claude-workers` session → worker's SessionStart hook registers it (`parent_manager_name=<manager funny name>` from env) → manager replies "spawned rebase-bot".

### F2. Worker question
Worker calls `ask_manager(sid, "conflict in X — ours or theirs?")` → question file in `questions/<manager>/` (and its topic copy) → the questions lane pings within ~2s → manager relays to user, then `answer_question(qid, "ours")` → worker's 500ms poll returns, worker resumes. The worker's tab turns red while waiting. If the manager stays silent past 12 h with a progress keepalive (1500 s when the client sends no progress token; Codex keeps its provider bound), `ask_manager` returns a `NO_ANSWER_YET:` sentinel and the worker re-calls with `resume_question_id` — the question file stays pending the whole time, so the manager sees one stable question.

### F3. Completion
Worker ends its task with `worker_done(sid, summary)` → done lane pings → manager surfaces the summary. Anyone can also block on it via `wait_for_worker(name)`.

### F4. Instruction
`send_manager_to_worker("rebase-bot", "also check migration order")` → typed straight into the worker's pane, prefixed `[MANAGER] `; submits immediately if idle, on next idle if mid-turn.

### F5. Manager recreation
`/recreate-manager` → `prepare_handoff` (snapshot + memory distill) → `spawn_replacement_manager` → new window `/manager-resume <id>` → `become_manager_with_takeover` closes the old window, inherits name + domain → workers and pending questions carry over untouched.

### F6. Crash recovery
Manager window dies: SessionEnd hook removes its record and runs the fallback memory distill. Workers keep running. A new `/manager` in the same situation (exactly one manager booting, orphaned workers) adopts legacy/orphan workers via the backfill.

### F7. Fleet pause and resume
The engineer, from a terminal outside the dockwright tmux server, asks the manager to quiet the fleet, then runs `dockwright pause` → daemon locks held, quiet check, manifest, stop files, launchd disable, workers archived with `fleet-pause`, managers closed, tmux killed. `dockwright resume` → each manager back on `claude --resume` with its name, notice delivered, then `daemon-stop` lifted; nodes wake on their events; the stop files under `[pause.hold]` stay until he lifts them himself. No session runs either command. `pause` needs `[lanes] in_manager = false` and a `dockwright.toml` that parses with a well-typed `[pause]`, and refuses while any session has a turn running or a busy input, a worker question is pending, a Codex session or a headless child is alive, or a worker holds a live subworker: close those through the manager first.

## Manager memory

Every manager close path distills the transcript via headless `claude -p` (model `[spawn].distill_model`, default `claude-sonnet-4-6`; transcript slimmed to ≤500KB; at most 400 words, re-asked once on overrun then cut to the budget with a first-line `[truncated: …]` notice; up to two `claude -p` runs of 180s each) into `~/.claude/dockwright/manager-memory/<domain>/<YYYY-MM-DD>-<sid>.md` — the six points of the Fable 5.1 compaction instruction. The writers: `prepare_handoff` (synchronous, on `/recreate-manager`), `close_manager_self` (on `/manager-close`), and the SessionEnd hook as a fallback that writes only when today's `(domain, sid)` file is missing. Boot (`/manager`, `/manager-resume`) loads the newest 3 files by mtime among the domain's last-7-days files. Domains exist to scope these memory pools (`/manager reviews` ≠ `/manager general`): the same domain shares one pool, and domains are isolated.

## Manager notebook (entry format + mechanics)

What the notebook is, and when to write and check it: `~/.claude/agents/manager.md` § Manager notebook. It complements manager memory: memory is a lossy 7-day narrative; the notebook is a lossless agenda. The format and mechanics live here.

**Location:** `<state_root>/notebook/<domain>.md` — one file per domain, auto-printed at boot by the `/manager` / `/manager-resume` memory-loader step (same skip-silently-if-absent contract as memory). Resolved/dropped entries move to `<state_root>/notebook/archive/<domain>.md`.

**Note topics — `dockwright notebook-migrate <domain> [--decisions MARKER] [--dry-run]`.** The command splits `notebook/<domain>.md` at each `## ` heading outside a code fence. Each section, verbatim, becomes the `context.ask` of a note topic `note-<domain>-<slug>` whose card (`kind: note`) takes the heading as its title and `[x]` as `status: closed`. The heading owns the note. Every run resets the note's title from the heading and its status from the checkbox, so a title or a `closed` status set with `topic_set` holds only until the next run. The slug is the heading's first four ASCII words. When two headings share those words, both keys also carry a hash of the full heading. So a note re-keys when you edit one of its first four ASCII words, when you edit any word of a hashed heading, or when you add a heading that shares its first four words. A re-keyed note is a new topic: the old note closes, and the new one starts at `P2` with none of the old note's links or summary. The text above the first section becomes the `context.ask` of the `fleet-<domain>` topic. A rerun syncs: a changed section updates its note, a section gone from the file closes its note, and an unchanged file writes nothing. After writing, the command reads the stored bodies back, joins them in order and compares them with the file; a difference prints a unified diff and exits 1. `--decisions MARKER` also joins every section whose heading holds MARKER into `decisions.<domain>` under `fleet-<domain>` and stores the marker in the fleet card, so a later run without the flag refreshes the registry. If no heading holds the marker, the run exits 1 before any write, for a passed marker and for a stored one whose heading was renamed. Pass `--decisions <new marker>` to re-point it. Pass `--decisions ''` to stop refreshing the registry from the notebook: the fleet card forgets the marker, the registry stays as last written, and every node footer of the domain keeps naming it as binding. Every node of a work in that domain finds the registry named in its footer. The notebook file stays the source: the command never edits it, and never reads the archive.

**Hourly note checks.** Every manager's stale lane runs, after each pipeline reconcile, the `check:` of every open note whose last check is at least an hour old; a lock per note keeps two managers off the same note. After 20 seconds a scan starts no new note, and no command of a started note but its first; a command it did not start records `timeout`. From the note's first `check:` line (`- check:`, `**check:**` and `- **check:**` count too) it takes at most five backtick-quoted commands and runs each without a shell, 15 seconds at most, only when it has at most four `|` stages and every stage is on the read-only list with every flag named: `gh pr|issue|repo|run view`, `gh pr checks`, `gh pr|issue|run list`, `gh api <path>` (a GET: no method, no fields), `git [-C dir] log|status|rev-parse|ls-remote|grep`, `ls`, `cat`, `test`, `wc`, `head`, `tail`, `grep`, `dockwright pipeline status <KEY>` and its short form `pipeline_status <KEY>`. `git ls-remote` takes a name of `[A-Za-z0-9_.-]`, never a URL; git reads a name that no remote carries as a local repository directory of that name. Git reaches only the `file`, `git`, `http`, `https` and `ssh` transports, and every command runs with only the absolute `PATH` entries. Only a leading `~` expands; `*` stays literal. Anything else records `refused`. The card gets `last_check: {at, runs: [{cmd, status, exit, output}]}` with `status` ok, failed, timeout, refused or error; a prose `check:` records empty `runs`. A stage that exits non-zero fails the command, except a stage its reader stopped — an upstream stage killed by SIGPIPE, or a stage cut at 64 KB of output — so `git log --oneline | head -3` records `ok`, as a shell reports it. A check runs in the note's `links.worktree` when that directory exists — set it with `topic_set` so `gh` picks that checkout's account. Set it, and write `git -C`, only for a directory you trust like your own checkout: git runs the commands its config names there (`core.fsmonitor`, a local remote's `uploadpack`, credential helpers). The pass prints nothing. A command that crashes records `error`. A note whose check crashes is skipped while the others run, and the lane pages `RECONCILE_ERROR * note-check RuntimeError: <note key>: …` at most once per 10 minutes; read that note's card and `context.ask`.

**Board — `dockwright board`.** A view of the store; its screens write nothing and take one `ps` snapshot each. `dockwright board [inbox] [--domain D]` prints what waits on you — every pending question but a subworker's, a manager's question to you included, every live session held at a plannotator gate or a permission dialog, every work whose `waiting_on` is `human:*`, and every reply a node or the topic agent wrote to your message in the last 7 days (`--serve` drops the ones this browser has opened) — then every pipeline work whose `waiting_on` is `stalled:<node>`, with the first sentence of its holder's last report. The line of a pipeline node's detached gate carries its plannotator link; once that process dies, the work's stopped line reads `gate lost — message the topic to reopen`. `--domain D` keeps lines of domain D and lines whose domain is unknown. `topics [--domain D] [--kind K] [--status open|closed]` lists every topic, freshest activity first; `--kind note --domain D` lists D's notes in the order of `notebook/D.md`, and reads that file itself while D is not migrated. `topic <KEY>` prints one topic in full; it lists decisions by `written_at` with `decided_by` and points at the domain registry, and it picks no winner between them. `--serve [--port N]` (default 8740) serves the same screens on `http://127.0.0.1:N/`. The inbox and topics pages reload every 30 seconds; their "Pause auto-refresh" link adds `?refresh=off` and stops the reload until you leave the page. Its pages also carry forms: on a topic page a message, a priority or new work, and an answer under each open question; on `/new` new work for a domain. Each form writes through `topic_message` as the engineer, and a form without the page's secret or from another origin is refused. The CLI screens print a notebook-migrate warning while a migrated domain's notebook holds edits `dockwright notebook-migrate` has not taken; the HTML screens do not. A topic page opens with its state in words, the delivery result of the message you just sent, the latest reply to you and the thread (your messages, pane lines, replies, your answers, gate verdicts, newest first); `--serve` marks a topic seen in the browser's `dockwright_seen` cookie when you open it. `/dockwright-threads` prints the inbox and the open notes of your domain.

**Sibling store — `<state_root>/tech-debt/<domain>.md`, deliberately NOT boot-loaded.** Scope split: `~/.claude/agents/manager.md` § Manager notebook. Same entry format plus a tag line (below), same per-domain split, same archive-on-resolve discipline; the read contract differs: read it ON DEMAND (before touching the subsystem an entry names, or when the user asks what debt exists), never in a boot brief. The tag line is the entry's second line, right under its `## ` heading: `- tags: <tag>, <tag>`, with every kind its items have — `defect` (a system we change in code behaves wrongly), `trap` (a measured behaviour or method error we do not change in code), `debt` (correct behaviour, costly shape), `idea` (a proposal with no defect behind it) — and every system it concerns, from `[tech_debt.systems]` in `dockwright.toml`, at least one of each. `dockwright tech-debt tags` prints both lists with their definitions. `dockwright tech-debt [--tag T]... [--domain D]` lists the matching entries as `<path>:<line>  <tags>  <title>`; its last line counts the untagged entries and the hidden headings, which no filter finds. A hidden heading is a `## ` line it reads as inside a code fence (a heading quoted in a fence, or an entry a broken fence hides), or a `# ` or indented `## ` heading after the file's title. `dockwright tech-debt --untagged` lists each with its reason and its repair. A tech-debt entry is at most 10 lines, and its `check:` is one backticked command that `--check` runs from any directory without `refused` (§ Hourly note checks names the commands it accepts). `--new` lists the entries absent from or changed since `<state_root>/tech-debt/.seen.json`; `--seen FILE` records the key and digest of each row of a `--json` listing in FILE. `--check` runs each listed entry's `check:` through the note runner and prints each result. `--archive FILE` archives the entries a JSON array of `{"key", "reason"}` names, as § Archive-on-resolve below does, into `tech-debt/archive/<domain>.md`; it writes nothing while a target's text holds a hidden heading.

⛔ **Do not teach the boot loaders about this file.** `boot_brief.py` prints a `NOTEBOOK` pointer only, and the four boot paths (`/manager`, `/manager-resume`, `/manager-reboot`, `/manager-takeover-recovery`) read that pointer only. That omission is the feature — the whole point of a second file is that debt does not ride into every manager's opening context. A trap that keeps biting belongs in a unit under `~/.claude/roles/_shared/fragments/<domain>/`, not in either file.

**Entry format:**

```markdown
## [ ] <imperative title>
- tags: <kinds>, <systems>   # tech-debt entries only: always line 2, right under the heading
- seen: <YYYY-MM-DD>, <YYYY-MM-DD>   # tech-debt entries only, optional: each date the defect was observed
- when: <the condition, in plain words>
- check: <named command or inspection that settles the condition in ONE cheap call — e.g. `gh pr view 54 --json state`, a ledger grep whose exact line shape is verified against the writer, or "today ≥ review-by">
- context: <links/paths that let a cold manager act — ticket, PR, doc §>
- added: <YYYY-MM-DD>, <manager name> (sid <first 8 chars>)
- review-by: <YYYY-MM-DD>   # surfaces for explicit triage if still unripe — no silent expiry
```

**Uncodified ruling.** A behaviour ruling of the user sets how a session acts in a case that recurs, beyond one named item. It binds from the turn the user gives it, and its home is a rule. Land it at once, or write this entry in the same turn:

```markdown
## [ ] Uncodified ruling: <the rule, one imperative line>
- ruling: «<the user's words, verbatim>» (<YYYY-MM-DD>)
- binds: <manager | workers | nodes | all>
- check: today ≥ review-by — then propose its home to the user; archive when the rule lands or the user drops the ruling
- added: <YYYY-MM-DD>, <manager name> (sid <first 8 chars>)
- review-by: <added + 14 days>
```

The heading holds no marker a `--decisions` registry reads. While the ruling binds workers or nodes, quote it in each brief or `topic_message` that reaches its case. By its `review-by`, propose its home to the user, in a periodic pass your operator runs or in the review-by triage below, and land what the user approves. Once the rule lands, or the user drops the ruling, archive the entry; an entry of another domain goes to its manager. The user's call on one named item is that item's state, never an uncodified ruling.

**`check:` must be settleable in one cheap tool call or a date comparison — not judgment.** A `check:` that parses another store's machine format (a ledger grep, a JSON field) must cite the owning writer's code (file:line) for the exact line shape it matches, or call a stats command that store ships — never a guessed grep. The event is named by its writer, not by the CLI verb that produces it — a check keyed on the wrong string silently reports "unripe" forever, the exact failure the notebook exists to kill.

**Archive-on-resolve.** When an entry is acted on or explicitly dropped: flip `## [ ]` to `## [x]`, append one outcome line (`- resolved: <date> — <what happened>`), move the whole block to `notebook/archive/<domain>.md`, and delete it from the active file. The active file stays small — boot warns above ~4 KB.

**Retirement is about the WORK being finished, not about the `[x]` marker.** The moment an entry's work is done, the WHOLE entry leaves the active file — even if the entry is still marked `## [ ]`, and even if something small is still open from it. Anything still open is re-filed as a FRESH, short entry stating only the remainder, with today's `added:` date and a one-line `re-filed from <archived header>` pointer.

⛔ **The anti-pattern: annotating a finished entry instead of retiring it.** Appending `✅ DONE` / `RESOLVED` / `CORRECTED` on top of a body that is now superseded, and leaving the whole thing in the active file. Each such layer is cheap on its own, which is exactly why they accumulate — the old body stays, the reader must diff the ✅ line against the paragraphs below it to work out what is still true, and the next update adds another layer. Engineer's instruction: completed notebook entries move to the archive in full, body included, so the active file does not silt up.

Applying it:

- **Finished, nothing open** → archive whole. Delete from active.
- **Finished, small remainder** → archive whole, then write a fresh entry for the remainder. Do not keep the original and trim it in place; a trimmed fossil keeps its stale header, its stale `added:` date, and its resolved history.
- **Genuinely still open** → leave it, but strip resolution history (what shipped, which PR merged, what a past reviewer found) down to what a cold manager needs to ACT. The narrative belongs in the archive.
- **Reference entries** (permanent facts, not tasks — e.g. "this failure mode looks like an outage but is a transient") never "finish". Say so in the entry's `when:` so a sweep does not retire them.
- **When in doubt between done and open, KEEP it** and say so. A wrongly-archived open item is worse than a slightly bloated file.
- **Re-check gates before trusting them.** A `when:` that blocks on a PR merging or a worker finishing goes stale silently: the entry then reads as blocked when the work is ripe, or as not-started when it is already in flight. Verify the gate's current state as part of any sweep.

**Review findings do not become notebook entries.** A finding from a code review is classified AT DISCOVERY as fix-now or dead. There is no third bucket, because no parking lot gets read — not the notebook, and not an issue tracker either.

**Scope — this governs where a finding is FILED, not whether it may be ignored.** Severity discipline is unchanged: a Critical or Important still blocks the merge until it is fixed or explicitly disclosed in the PR body (the operator's review-discipline rule), and such a disclosure ships inside the change under review rather than sitting in a queue nobody rereads — so it is not the third bucket this rule rules out. What dies is the separate tracker entry, never the obligation.

The discriminator is whether the finding DEMONSTRATES its failure. "I ran X and observed Y" is a real finding: fix it now, in the same loop. "This could be wrong", "both one-liners, no failure mode", "non-blocking Minor, deferred to keep the merge unblocked" is a cosmetic finding: it dies with its PR. The thing that makes this safe lives on the reviewer side, not the parking side — require a finding to demonstrate its failure before it counts as blocking, and the ones worth keeping are exactly the ones that survive.

Why filing is not a safe fallback: **a "no failure mode" label is the defect, not the parking place** — a finding nobody can demonstrate is cosmetic, and one somebody can demonstrate should never have been deferred.

Applied to an existing notebook: sweep out every entry that is a review residue asserting its own harmlessness, and keep the ones recording an observed misbehaviour. Everything swept still goes to the archive in full — the archive is the record, it is just not an agenda.

**Review-by triage.** ⛔ Run an expired entry's `check:` BEFORE putting it to the user — the agent file's § Manager notebook re-derivation gate binds this triage, and an expired entry is the likeliest one to be dead already. Then triage explicitly with the user: re-date, drop (archive with a reason), or act now. Never silently re-date.

**Gardener stays separate.** The Gardener ledger (`~/.claude/dockwright/gardener/ledger.jsonl`) is machine-parsed JSONL with its own piggybacked check cadence — it does NOT move into the notebook. Notebook entries may reference ledger state in their `check:`, linking by reference.

## Lanes

The manager core names when to run `dockwright lanes`; this is how to read it. § Lane monitors holds the exit-code table.

- **A dead lane ends.** Each lane is one `dockwright monitor-loop <lane>` process; on exit the harness prints `Monitor "dockwright <lane> lane" script failed (exit N)`. An orphaned lane ends itself the same way.
- **`dockwright lanes`** prints one row per lane: `OK`, `BACKLOGGED`, `ARMED-UNRESOLVED`, `STALLED`, `HUNG`, `DEAD` or `NEVER-ARMED`. It exits non-zero if any row is not `OK`. `HUNG` needs a `kill`: the process is alive, holds the lock so a fallback exits as a duplicate, and has stopped iterating. `ARMED-UNRESOLVED`, `STALLED` and `HUNG` mean alive. `BACKLOG NOT CHECKED` means nobody looked.
- **`IN-DAEMON`** means the lane runs in the daemon ([lanes] in_manager = false); only `pages` is yours. Nothing to arm.
- A fallback restores future delivery. Consumed events are gone: check `list_workers` and `list_pending_questions` after arming one.
- `[plugin monitor "<desc>" suppressed N events — output rate exceeded]` comes from the harness. Re-query `list_pending_questions`, `list_workers` and `get_worker_summary`.

## APPROVAL_PROMPT pages

The `PermissionRequest` hook writes a marker for every permission dialog of a dockwright session before the dialog is drawn, and the stale lane pages `APPROVAL_PROMPT <name> → … — <tool>: <command>` once per dialog, within about 60 s, with the first 160 characters of the command in the line (a cut ends in `…`): a gated command, a "sensitive file" path, an edit under `~/.claude`. A pre-registration trust or MCP boot dialog on a pending spawn pages from the pane the same way. There are no 5-, 10- or 20-minute repeats: a new dialog pages at once, and `STALE_PROCESSING` stays silent while the marker is open and the pane still shows the dialog. Under the headless preset these are the commands the classifier declined; during a classifier outage, every Bash call outside the allowlist.

1. `get_worker_pane(<name>)`, always: the pane text, `dialog_sign` (a dialog box with its title is on screen), `classic_dialog` (question and options visible), `prompt_at` (the value the answer takes), `prompt` (the marker and its state) and `human_attached`.
2. If `human_attached` is true, the input box holds text, or the visible transcript shows the engineer's own message, leave the pane alone.
3. Read the whole command from `prompt.summary` or the pane text, never from the line alone.
4. A command that fits the task and destroys nothing: `answer_permission_prompt(<name>, approve, prompt_at=<its prompt_at>)`. The answer and the command land in `permission-answers.jsonl`.
5. A destructive, out-of-scope or credential-touching command: `answer_permission_prompt(<name>, refuse, prompt_at=<its prompt_at>)`, then redirect the worker or escalate with the verbatim command.

`prompt_at` binds the keypress to the pane you read: pass `get_worker_pane`'s top-level `prompt_at` as returned, a number for an open marker and null for a classic dialog with no open marker (a pending spawn, a closed or unknown marker beside a visible dialog). A different value returns `changed` and presses nothing; read the pane again. The tool presses a key only when a dialog is on screen, and reports `changed`, `no_dialog`, `human_attached` or `wrong_dialog` when it pressed nothing, and `unsettled` when the dialog stayed after the keypress; on `unsettled` a second call is allowed. An edit under `~/.claude` (skills, rules, agents, settings) draws a harness dialog ("Edit file … Do you want to make this edit …") that no preset clears in advance; its second option reads "Yes, and always allow access to … for this session" on an edit that resolves through a symlink, and "Yes, and allow Claude to edit files in its ~/.claude folder for this session" on the self-modification variant. `answer_permission_prompt(<name>, approve_session, prompt_at=<its prompt_at>)` presses 2 only when the folder option text is on screen and covers a batch; on `wrong_dialog`, answer `approve` per edit. Implementer subagents are denied those edits by the classifier, so a plan routes them to the top-level worker session.

The hook approves nothing. On a Bash command that names a tool-results file through a pool account's `~/.claude-<x>/projects` symlink, it denies with the real path under `~/.claude/projects` and the worker re-runs the command itself; no dialog is drawn. `permission-answers.jsonl` holds every such `deny-hint` and every manager answer. Raw `send-keys` remains only for a ghost pane the tools cannot find.

## SAFEGUARD_PAUSE pages

Claude Code can pause a session on a safeguard flag with a "Session paused" dialog: "1. Switch to <fallback model>" and "2. Edit prompt and retry with <model>". The session waits there until someone picks an option, and the default selector sits on the model switch.

The stale lane clears the dialog on a worker when two signals agree: the transcript's last event is Claude Code's "stopped by a safety classifier" note, and the dialog is the bottom-most prompt on the pane (the last `❯` line is its selector, under a "Session paused" line, beside an "Edit prompt and retry" option). With `CLAUDE_ORCH_AUTONUDGE=1` it presses that option's number, waits up to 5 s for an empty input line, types `continue`, and pages `SAFEGUARD_PAUSE <name>`. It never presses Enter while the dialog shows and never picks the model switch. With a human at the pane it does nothing and pages nothing. It stops, and pages the manual steps, when:

- autonudge is off;
- the same worker flags again within 30 min of the lane's retry;
- the input line does not come back empty after the keypress: the dialog stayed, or Claude Code put the refused prompt back on the line;
- `continue` does not submit.

Each flag pages once, and the lane never acts again on a flag it paged: that flag waits for the engineer. A dialog the lane did not clear still pages `STALE_PROCESSING` from 30 min. On a page from one of those cases, follow its step: it names the pane and what the engineer does there. Never relay into that pane: the relay ends in Enter, and Enter picks the model switch. Manager panes are outside the lane; an interactive subworker (`claude-tui`) is inside it.

## Classifier outage

In auto mode the runtime asks a model to vet every Bash command. During an Anthropic-side model outage every Bash call is gated: the worker reports `... auto mode cannot determine the safety of Bash right now`, and a re-ping does not help. Workers can still Edit, Read and Write, but cannot run `git`, `gh`, a build or `worker_done`. The manager runs in auto mode too, so only its allowlisted commands keep flowing.

- Spawn and respawn workers with `extra_args=["--model", "@opus", "--effort", "xhigh", "--dangerously-skip-permissions"]`. Local commits persist: kill the gated worker and respawn at the same cwd with a tight brief on what is left (`last_summary` names the pushed HEAD).
- Run a one-off gated `gh` or `git` step yourself.
- Return to default spawns once the outage clears.
- An ungated manager: recreate it with `DOCKWRIGHT_MANAGER_SKIP_PERMS=1` in the launch environment. The launcher clears the variable at server birth, so a plain recreate reverts it.

## Sandbox driver

The host session that drives a sandbox E2E dogfood (an isolated VM reached over compound `ssh`, VM-CLI and `tmux` pipelines, exercising a build inside that VM) runs with `--dangerously-skip-permissions`. A manager acting as that driver is recreated with `DOCKWRIGHT_MANAGER_SKIP_PERMS=1` in the launch environment; the default launch stays auto.

The exemption covers a driver that is not itself under test and that the VM boundary contains. E2E work in general does not qualify. Everything inside the VM stays product-default: a VM-side bypass invalidates the run.

## Accounts

`~/.claude/dockwright/account-active` holds a name from `[accounts]` in `dockwright.toml` (default pool: the single account `a`; more through `[[accounts.pool]]`). It selects the account every new spawn bills. Each account's login lives in its own config dir, which `config_dir` can relocate.

- **The flip.** The stale monitor flips `account-active` when the active account bricks on a limit banner: a 30-minute cooldown (`CLAUDE_ORCH_FLIP_COOLDOWN_MIN`), and no flip onto an account inside its own reset window. The audit trail is `account-flips.jsonl`.
- **Hold.** The "Your account is on hold" API error in a session's transcript marks the account `held` in `account-state.json` with no reset: spawns, flips and resumes skip it, the monitor points `account-active` away without the cooldown, closes every claude worker and subworker stamped with that account, healthy or not, since each dies on its next call (`closed_reason: "account-hold"`), recovers a held manager through its own limit branch, and pages `ACCOUNT_HOLD` once per manager. `dockwright account-hold <name> [--reason TEXT]` holds an account by hand (running sessions finish on it), `--release <name>` is the only way back, no args lists holds; `dockwright doctor` shows them.
- **Rollback.** `echo a > ~/.claude/dockwright/account-active` forces an account. Removing the file disables the feature (keychain auth).
- **Logins.** Each account is logged in once: the default in a bare `claude`, the others in `CLAUDE_CONFIG_DIR=~/.claude-<name> claude`.
- **Per-model windows.** `usage/<account>.json` also carries `model_scoped` (`[{name, pct, resets_at}]`, today the Fable weekly window) and `model_scoped_at`, read from the last `/usage` snapshot in that account's `.claude.json`; no snapshot gives an empty list. Open `/usage` in a session of that account to refresh it. An account's Fable is marked spent in `account-state.json` (`model_spent`) when a worker or subworker session on it shows the Fable-limit banner. The `StopFailure` hook writes the mark at the refusal. For a session the hook missed, the stale monitor writes it on its next pass from the newest banner in the transcript tail. A manager's banner marks nothing. A spawn on Fable skips an account whose snapshot is at or over `usage_pause_pct` before its `resets_at`, or whose mark is still in force. It also skips an account near its 5 h/7 d limit unless forced. With no account left, or when the account it launches on has spent Fable (the pool is off, or a farm falls back to the default account), the spawn launches on Opus at effort `xhigh`, or `max` when asked. A banner counts only when it is no older than the session's current launch (`started_at`). A mark ends at a newer snapshot, at the snapshot row's `resets_at` when that is later than the mark, otherwise at the account's first seven-day reset after the mark, and in every case seven days after the mark. Removing a mark by hand lasts only until the next pass while a live session's transcript tail holds that banner.

The default account's config is `~/.claude.json` at the home root (`paths.HOST_CLAUDE_JSON`): the projects map, the trust list, MCP approvals and `oauthAccount`. `~/.claude/.claude.json` is a different file; a skeleton of about 1.6 KB there is what a wrong probe writes. Other accounts keep theirs at `~/.claude-<name>/.claude.json`.

1. Probe the default account with `env -u CLAUDE_CONFIG_DIR claude -p ...`. An explicit `CLAUDE_CONFIG_DIR=~/.claude` reports `Not logged in · Please run /login` on a healthy account and writes the skeleton. Other accounts take the explicit variable.
2. Judge the default account's health from `~/.claude.json`: a healthy file has about 107 top-level keys, a populated `projects` map and `oauthAccount`.
3. `~/.claude/backups/` holds backups of the home-root file, one per CLI start. Compare sizes before you conclude anything from them.
4. Before you report a config loss, compare both paths: size, key count, `projects` count, `oauthAccount`, mtime, and the backup sizes.
5. `dockwright doctor`'s `accounts:login` check reads `~/.claude.json` for `oauthAccount`. A PASS shows the marker, and an expired token still fails with 401 while the marker stands. Cite doctor for "never logged in" only; liveness belongs to the AUTH_401 lane.

A second probe confirms the first only when it derives the target file by itself.

## Throttled workers

A worker in `state=processing` whose `last_summary` carries `Server is temporarily limiting requests (not your usage limit) · Rate limited` (a 429) is stuck: it sends no `worker_done`, does not flip to idle, and does not resume. Send `send_manager_to_worker(<name>, "resume your task")`. This is a different signal from `STALE_PROCESSING`. When you see one, sweep `list_workers` for the same text and ping each match. A `wait_for_worker` downstream unblocks once the upstream worker finishes.

## Degraded status

`queued_no_window`, `degraded=true`, a fallback that fired, a swallowed or abstained step: each means the primary path failed. On the first occurrence, stop and find why it failed before you rely on the fallback.

## Known proxies

A field's name is not its definition. These dockwright signals answer a different question from the one their name suggests.

- `state=processing` with a work-shaped `last_summary` does not show that the worker is working. `last_assistant_summary` returns the last completed turn, and `state` has two writers (`hooks.py` at turn start, `mcp_server.py` for an idle delegator). The `alive` field beside it is a live pid check. `RESUMED` means the transcript grew, and a session-limit banner grows it as much as work does.
- `setup.sh` exit 0 says the command succeeded. It does not say its input was right: it can deploy from a clone parked on another feature branch, and it prints a stderr warning that names the branch.
- `candidates` in a prune scan counts every worktree scanned. The eligible count is `summary.would_remove`.
- A file inside your domain's repo does not make the work yours. The owner is whoever is writing it now.

## Two-tier verification

The author of a diff classifies it and runs its review; the manager owns no review lane. The first match wins.

- **Tier 2:** the diff touches a behavioral surface (`deploy/**`, `src/dockwright/**`, `tests/**`, `evals/**`, `scripts/**`, `publish/**`, `.github/**`, `setup.sh`, `pyproject.toml`, `uv.lock`, any migration, any spawn, kill or hook script), or any code or config file (`.py .sh .bash .groovy .kt .java .ts .tsx .js .jsx .go .rb .rs .c .cpp .swift .json .yml .yaml .toml`, `Dockerfile`, `Makefile`), or more than 100 LOC by `git diff --shortstat origin/main..HEAD`. When unsure, Tier 2.
- **Tier 1:** everything else. Read `git diff origin/main..HEAD` and check for a reference that no longer exists, a claim that contradicts the known system, a structural break, and scope past the PR title. Post the PR comment `Tier 1 verification (prose, N LOC, no code)`.
- **The Tier-2 loop:** one reviewer session for every round, told READ-ONLY in its brief, with no write tools, given the full `origin/main..HEAD` diff and the author's claims verbatim. The author reproduces each finding before fixing it and sends the fix to the same reviewer. A fix to prose only (PR body, code comment) opens no round. An APPROVE holds: later rounds review the delta and what it reaches. Three rounds are recommended, and an APPROVE does not reset the count; past them the author judges convergence and cuts or reshapes; a Critical or Important the author would leave goes to the manager.
- **The record:** each verdict is published in the reviewer's own words, as a `review`-phase artifact or a PR comment.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `/manager` says MCP not connected / `become_manager` not found | MCP servers live in `~/.claude.json` (via `claude mcp add`), NOT `~/.claude/settings.json` | `claude mcp add --scope user dockwright dockwright mcp-server`, restart session |
| `list_workers` / monitors return other managers' stuff, or a stderr "did not resolve to an active manager" warning | You passed the manager's **funny name** as `manager_sid` — it takes the session UUID | Pass `$CLAUDE_CODE_SESSION_ID` (or Codex `$CODEX_THREAD_ID`) |
| Worker spawned but its events never reach the manager | Worker is UNSCOPED (`parent_manager_name=null`) — spawned with `manager_sid=None`/omitted (an unresolvable sid now rejects at spawn instead of spawning unscoped) | Respawn with the correct `manager_sid`; or boot a single manager so `_backfill_legacy_workers` adopts it |
| `spawn_worker` raises a tmux-spawn error | tmux server unreachable on the dockwright socket | Confirm tmux is installed and can start a server on `-L dockwright` (socket override: `DOCKWRIGHT_TMUX_SOCKET`; legacy `CLAUDE_ORCH_TMUX_SOCKET` honored one release) |
| Worker blocked but manager sees no question | the lane missed it or scoping issue | `list_pending_questions(manager_sid=<sid>)`; for legacy flat questions use `manager_sid=None` |
| Worker pane gone, no SessionEnd fired (kill -9, OOM) | Orphan active record | `_prune_stale_active_records` runs on most tool calls and reaps dead-pid records automatically; worst case `rm active/<sid>.json` |
| A pipeline node's pane closed a minute or two after its `worker_done` | Node autoclose: the token had left it (or its terminal node had every output complete) and it reported | By design; its `events.jsonl` carries a `HANDED_OFF_CLOSED` lane_event with the reason. A node parked at a gate, holding a pending question, or attached to the engineer is never closed this way. A closed finished terminal node is not resumable: `resume_worker` says the node finished; start new work or a topic instead |
| Worker disappeared after hours idle | 2h idle auto-close by stale_monitor (by design) | `list_closed_workers()` then `resume_worker(name)` — full history comes back |
| Old MCP server lacks `prepare_handoff` / `runtime` args | Server booted before the code shipped | `bash ~/.claude/scripts/bootstrap-recreate.sh …` writes the handoff + spawns the replacement directly |
| A lane reads `DEAD` in `dockwright lanes` | the lane process ended (see the exit-code table) | follow the recovery line: fallback `Monitor(dockwright monitor-loop <lane>)` or recreate the tab |
| No QUESTION/DONE lines arrive and `dockwright lanes` shows `IN-DAEMON` | the daemon is down or stopped | `dockwright daemon status`; `dockwright doctor`; read `~/.claude/dockwright/daemon/launchd-err.log` and `launchd-wake-err.log`; `dockwright daemon tick` by hand |
| A lane scan cannot resolve its owning manager | Identity resolution failed (no `TMUX_PANE` match, PPID-walk miss) | Check `active/` has a manager record with your `window_id`/pid; re-run `/manager` |
| Two sessions share one transcript after `/manager-assign` | Expected: the old window is a stale duplicate | Close the old window |
| Hook commands missing `CLAUDE_PARENT_PID` | Hand-edited settings.json | Re-run `./setup.sh` — idempotent merge |
| Child window still open after the round | Latest round stays for its parent to read | `kill_child(name)`; superseded rounds and orphans are closed by the stale monitor |

## Verification fixtures + tmux panes

- For a test needing a pane in a specific process state, launch a raw command (`sleep`, `cat`) in a tmux window rather than a worker — claude won't reliably sit on a blocking syscall.
- The `window_id` a spawn returns is a tmux **pane** id (`%N`); pane ids and window ids are separate id-spaces. Address a worker's pane by its pane id (`kill-pane -t <pane_id>`, `send-keys -t <pane_id>`), never a bare window index.

## What it can't do (still deferred)

- Hierarchical sub-managers (peer managers exist; a manager can't own another manager)
- Worker-to-worker messaging (only `wait_for_worker` on a sibling's completion)
- Per-agent `--allowedTools` / permission scoping (workers only get remote-control-off settings)
- Persistent worker pools / pre-spawned roles (presets cover prompt boilerplate only)
- Web / GUI status view (`status` is terminal-only)
- Cross-machine orchestration
- **Real mid-turn interrupts.** Direct send-text lands immediately only if the worker is idle; mid-turn it buffers. "Stop now" = `kill_worker`.

## How this differs from in-process `Agent` subagents

The Claude Code `Agent` tool spawns subagents *within* one session — same process, results return into the parent's context, gone at session end. dockwright spawns **separate CLI processes** in **separate tmux windows**: own context windows, own transcripts (`~/.claude/projects/` / `~/.codex/sessions/`), survive the manager, human-readable scrollback, resumable after close. Trade-off: filesystem comms (~500ms answer poll, ~2–5s monitor latency) and no shared memory.

Use `Agent` for "search 5 things in parallel right now". Use the orchestrator for "hours of independent work running in tabs while I do other things".
