# /manager-resume

You are taking over manager duties from a previous manager session. Do the following in order:

1. Parse `$ARGUMENTS` for the `handoff_id`. If missing or empty, tell the user "ERROR: /manager-resume requires a handoff_id" and stop.
2. Read `~/.claude/dockwright/handoffs/<handoff_id>.json`. If the file is missing, tell the user "ERROR: no handoff with id <handoff_id>" and stop. If `consumed_at` is non-null, tell the user "ERROR: handoff <handoff_id> already consumed at <consumed_at>" and stop.
3. Resolve `<your sid>` from the session id in system context / `$CLAUDE_CODE_SESSION_ID` (managers run under Claude Code). If you need to inspect it from shell, run `printenv CLAUDE_CODE_SESSION_ID`. Do not invent or synthesize a sid.
4. Call the `dockwright` MCP tool `become_manager_with_takeover` with `claude_sid=<your sid>`, `takeover_from=<the handoff's from_sid>`, and `handoff_id=<id>`. If it returns an error, surface it and stop. It returns your `name` and `domain` (and `runtime`, always `claude`). It also paints your tmux tab (name · domain) and runs preflight cleanup server-side — surface the returned `preflight` line to the user if non-empty (older orchestrator builds may omit the field; then skip silently).
4b. **REQUIRED — confirm the predecessor's pane is closed.** `become_manager_with_takeover` closes the predecessor's tmux pane automatically via `get_driver().close()` (tmux `kill-pane`). Check the return's `predecessor_pane_closed`. If `false` (or the field is absent on an older orchestrator), verify manually — `tmux -L "${DOCKWRIGHT_TMUX_SOCKET:-${CLAUDE_ORCH_TMUX_SOCKET:-dockwright}}" list-panes -a -F '#{pane_id} #{window_name}'` and `kill-pane` any pane still carrying the predecessor's name (this manual path will prompt for approval — it is the rare path). Two live managers for one handoff is a split-brain state — do not skip.
5. Call the `dockwright` MCP tool `attach_existing` to enumerate workers and orphan questions (they carry forward from the old manager).
6. If your system prompt already contains the line `<!-- dockwright-role: Manager launch=manager -->`, your manager definition is loaded: skip this Read. Otherwise load the manager definition from `~/.claude/roles/Manager/role.manager.md` when that file exists, else from `~/.claude/agents/manager.md`. **This file (~46 KB / 388 lines shipped; an operator overlay adds to that) can with an overlay exceed the ~25k-token single-Read cap, so one `Read` silently truncates it — the later sections just never arrive, with no error.** You MUST page it to EOF before acting: the total line count N is the `AGENT_LINES <N>` line printed by `dockwright boot-brief` (step 7 below). `Read` the file in windows of ≤200 lines (`offset=1`, then `offset=201`, then `offset=401`, … each with `limit=200`) until a window reaches line N. **Do not act on a partial read** — if the last line you have read is below N, page again. Only once the whole file is in context, follow its operating principles for the rest of this session.
7. Load recent manager memory + the manager notebook for your domain. The handoff record carries the predecessor's `domain` and `manager_name`; the `become_manager_with_takeover` return value gives them back too. Run `dockwright boot-brief --domain <domain>` (substitute `<domain>`). It prints AGENT_LINES plus **paths only** — `Read` each printed `MEMORY <path>` and the `NOTEBOOK <path>` with the Read tool (Read paginates, so nothing is dropped). It prints pointers rather than file contents because the memory distills + the notebook can overflow the Bash inline-output cap, leaving only a ~2 KB preview in context — silently dropping memory and notebook content (this is why an old inline-`cat` boot could falsely report the notebook empty). The `MEMORY` pointers are the newest 3 files by mtime among those from the last 7 days (boot-cost cap). Fold these into your working context as predecessor context (your immediate predecessor's just-prepared distill is in there too — it's the newest file, so the cap never drops it). Skip silently if none printed. The `NOTEBOOK` pointer is your domain's current-state agenda (`~/.claude/dockwright/notebook/<domain>.md` — see `~/.claude/agents/manager.md` § Manager notebook): if it printed, count its unresolved entries — every `## ` header not marked `## [x]`, the same selector the agent file's § Manager notebook names, because a ruling entry carries no checkbox and `## [ ]` silently misses it, evaluate which look ripe (date conditions by inspection; others via the entry's named `check:` command — one cheap call each), and add "N unarchived entries, M look ripe" to the takeover brief, flagging any entry past its `review-by` for triage. ⛔ Naming a specific entry in the brief is a RELAY, and the agent file's § Manager notebook gate binds it: run that entry's `check:` first. A brief that only COUNTS entries asserts nothing and needs no check. If boot-brief printed a `NOTEBOOK_WARN` line, archive resolved entries per the agent file. If no `NOTEBOOK` line printed, skip silently — no mention in the brief.
8. Surface a 3–5 line takeover brief to the user:
   - "Took over from <from_sid[:8]> (trigger: <trigger_reason>). N workers in flight, M pending questions. Loaded N memory files (newest 3 within last 7 days)."
   - The first paragraph of the handoff's `narrative_summary`, verbatim.
9. Arm the four lane monitors. Invoke `Skill(dockwright:arm-lanes)`. The dockwright plugin then starts the four lane monitors (`dockwright monitor-loop questions|done|turn-ends|stale`); a lane already armed in this CLI process is skipped, so the call is idempotent. Wait 10 s (`sleep 10`) before the first `dockwright lanes` — arming lands about 5 s after the skill call and a lane needs one more scan to heartbeat, so an immediate read shows `NEVER-ARMED` or `ARMED-UNRESOLVED` rows on a healthy install; if any row reads `NEVER-ARMED` or `ARMED-UNRESOLVED`, run `dockwright lanes` once more after another 10 s before you follow its recovery line. For any row that is still not `OK`, do what its recovery line says; the fallback it may name is a degraded mode — say so in your brief. Lane output: `dockwright-orchestrator-guide` § Lane monitors.
9b. Model check. Run `dockwright model manager '<your id>'` alone, with nothing chained to it, where `<your id>` is the model id your system prompt states, in single quotes. The command resolves the id a manager launch gets from the install on disk right now and prints `same <printed id>` or `differs <printed id>`. Act on that word alone, even when the printed id carries a `[1m]` your id lacks. On `differs`, tell the user: "This manager is running on <your id>; the manager lane is specced for <printed id> — run `/recreate-manager` in this pane; the recreate launches on the lane's model and effort." Never put a `@` token in that line: the CLI answers `unrecognized_model` for a token. If the command exits non-zero, tell the user its stderr instead. Either way it is a warning, not a gate.
10. From this point on, the user is in manager mode. Confirm with: "Manager active (resumed from <from_sid[:8]>)."
